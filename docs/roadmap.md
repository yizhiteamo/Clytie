## 阶段一：架构

### A1 工程与 SDK
范围：
- `pyproject.toml`、`.gitignore`、`.gitattributes`、`.pre-commit-config.yaml`、GitHub Actions、`README.md`、`LICENSE`
- `clytie.sdk`：`sdk-spec.md` 中的全部数据类型、取消与时钟协议、扩展点签名和合并规则的定义（可以先不实现本体）
- 配置与 Schema 按 `config-spec.md`；`status` 命令的边界见其第 7 节
- `sdk.testing`：每个接口的契约测试套件、模拟时钟
- `schemas/`：plugin、companion、instance 的 JSON Schema
- `config`：分层配置加载与校验；`examples/home/`（虚构数据）
- 参考插件 `fake-model`、`fake-channel` 通过契约测试

验收：
1. 仓库中没有实例目录内容、凭据、数据库；通用扫描和私有名单扫描都通过
2. 每个 SDK 接口都有契约测试，假实现全部通过
3. SDK 数据类型都可以序列化和反序列化（往返测试）
4. 所有接口支持取消；与时间相关的代码只使用 `ctx.clock`（附检查方法）
5. `examples/home/` 通过 Schema 校验；故意写错的配置能给出可读的错误位置
6. 仓库中不存在任何部署专属名称和旧系统路径

### A2 插件宿主
范围：发现、清单校验、依赖解析、扩展点注册与分发、行为指令合并规则、`ctx` 权限裁剪、故障隔离与安全默认值、按伴侣启用、热加载、私有状态与升级脚本、卸载保留数据、`catalog.json` 生成。参考插件：`echo-tool`、`example-behavior`、`keyword-retriever`、`desktop-notifier`。

验收：
1. 缺少依赖时拒绝并给出补齐方案；版本冲突、`conflicts`、依赖环都能检出并说明原因
2. 未声明的权限在 `ctx` 上不存在（测试尝试访问会失败）
3. 插件抛出异常时，本体和其他插件继续运行，并采用安全默认值
4. 多个行为插件给出冲突指令时，结果符合合并规则且可复现
5. 停用被必需依赖的插件前有提示；可选依赖方收到"服务不可用"事件
6. 升级前自动备份私有状态；卸载后私有状态仍在
7. 本体模块无法停用
8. 静态检查：`plugins/` 下的代码只 import `clytie.sdk`
9. 一个只在测试中定义的新插件，不修改本体就能接入每一种扩展点

其他文档中的“A3”统指 A3.1–A3.4。任务编号查重分配、取消结果转换、截止时间触发、取消宽限期与账本写入，随 A3.1 的账本及取消快速路径验收；模型和工具循环中的取消贯通在 A3.2 完整离线路径中验收。A1–A3 仅声明管理接口的约定保持不变，管理服务在 A4 实现。

### A3.1 账本与交付
范围：统一账本、防重、交付与收据、事件总线、调度器、`python -m clytie task <编号>`。本阶段验证账本与交付离线路径，完整模型/工具对话链路在 A3.2 完成。

验收（承接原 A3 第 1、3、4 项及相关 L 项）：
1. 账本与交付路径离线跑通；日志有追踪号、任务编号、各阶段耗时；`python -m clytie task <编号>` 可查。原第 1 项的完整对话链路验收由 A3.2 完成
2. 重启后未完成任务不重放；发送结果未知不补发；取消快速路径有效
3. 表情只用于任务；未声明例外的插件无法加表情
4. L2 的统一账本基础和 L5 的表情规则有离线回归并通过；事件总线有离线测试，调度器用模拟时钟验证

### A3.2 对话主干
范围：agent 工具循环、能力状态注入、人设分层、边界与出站检查；接入 A3.1 账本与交付，结束时完整离线路径跑通：假平台消息 → 上下文 → 假模型选择 `echo-tool` → 权限 → 执行 → 账本 → 交付。

验收（承接原 A3 第 6、8 项，并完成原第 1 项完整路径）：
1. 上述完整路径离线跑通，追踪号、任务编号、各阶段耗时及任务查询贯通
2. 越界请求被拦截；达到阈值后停止回应并通知；正常玩笑不计入
3. 出站检查：对外场景中出现内部名字时被拦截
4. L1、L3、L4 有离线回归并通过；L2 从统一账本接入对话，回答与实际执行记录一致

### A3.3 记忆核心
范围：存储、可见等级与来源会话投影、修订与撤销、当场记与可信程度、语义与关键词检索、上下文接入、私密记忆出站检查、加密导入导出和 L6；接入已有对话与账本路径。实现契约及全部 15 项离线验收见 `architecture/memory-spec.md` §11。

验收（承接原 A3 第 5、7 项）：
1. 可见等级：群聊场景检索不到私密记忆（包括通过插件的记忆视图）
2. 记忆导入导出：加密包校验；三种导入模式；导入前自动快照并可撤销；重复导入不产生重复；空库不能覆盖已有记忆
3. L6 的账本与记忆联合证据检查有离线回归并通过，查不到时不接受虚构前提

4. 当场记按主人身份提供工具，可信程度由本体填写；去重、修订冲突、撤销、写入失败和写入上限有回归
5. 关键词与语义融合、可选重排、降级及向量重建有离线证据；上下文按预算整条注入，主动消息使用目标场景
6. 私密记忆泄露改写一次，仍命中则拦截；改写提示、日志和审计不包含私密原文
7. 从零开始，无预置记忆；投影为空时注入固定说明；首条记录产生身份标识，空库拒绝导出；导入仅支持把她自己的记忆搬回她自己

### A3.4 回想与印象
范围：对话结束后的回想整理、群内经历、群友印象、软遗忘与想起即加深、黑话，以及 Issue #33 的 O1、O2。实现契约见 `architecture/memory-recall-spec.md`；只处理之后的新对话，不回溯账本。看图与认出形象不属于本里程碑。

验收（与 memory-recall-spec §10 一致）：

全部使用假模型、假向量模型、MockClock 和虚构数据。

1. **触发**：安静 30 分钟后回想一次；有新消息才回想；陌生人私聊不回想；群里主人和她都没出现时不调用模型但推进进度；每日上限生效。
2. **出处**：没有出处、出处编号越界、`core:with_owner` 与出处说话人不符的条目被丢弃并记审计。
3. **别人说的话**：群聊窗口中假模型返回 `fact`、`preference` 时被拒绝；"某人说主人……"只能作为经历写入，不进入核心记忆，不改变主人的记录。
4. **不用记**：窗口中她撤销过的内容，回想不会重新写回（规范化相同、假向量模型下相似度超过阈值的都被丢弃）；扩展收到的窗口中没有从撤销记录派生的内容或编号（聊天原文保持原样）；对话模型请求、日志和审计中没有撤销原文；向量模型出错、超时或未配置时退为只做规范化比对，回想照常写入并推进进度，`status` 有提醒；临时计算的撤销向量不写入向量表。
5. **合并**：只合并全是 `observed` 的记录；含主人记录时不动；修订和撤销可追溯。
6. **防重与恢复**：回想写入和进度推进是一个事务；模拟中途崩溃后重新回想不产生重复；取消时不写入；新实例或导入后不回想以前的账本。
7. **投影**：群聊回想读不到私密记忆；群聊经历在其他普通群不可见、在对内场景可见；私聊经历在群里不可见。
8. **印象**：群聊中只在对方在场（说话、被引用、被提到）时注入，不在场时普通检索和 `core_recall` 都不返回；对内场景只在检索命中时带上，不无条件放入全部印象，计入想起的预算；注入文字不含来源群；群友没有写入入口；主人私聊中可以撤销；对方没说话时不调用模型。
9. **淡化**：MockClock 推进时间，会淡的记录排序下降，到阈值冻结；永不淡化的类别（含 `core:with_owner`、家庭群来源的经历和黑话）不受影响，`observed` 的群友印象照常淡化，主人修订过的印象和黑话不淡化且不进核心记忆；主人参与学到的黑话没有 `core:with_owner`，照常淡化；`origin_conversation_id = null` 的非印象记录不淡化；淡化不产生修订。有重排时：正负重排分都不会让淡化的记录排到更前面；重排同分的共用名次；候选段从未乘淡化系数的顺序选取，候选段外的记录接在后面；重排返回 NaN、无穷大或长度不符时按重排不可用处理。
10. **加深**：被注入或被 `core_recall` 命中后半衰期变长；冻结记录被主动回想命中时解冻。
11. **永不删除**：任意时间推进后记录都还在库中。
12. **黑话**：所属群按普通检索想起，与其他记忆共用预算，不无条件放入全部黑话；对内场景标注"只听懂"；其他群不可见；插件不能写别的群。
13. **搬家**：群聊与私聊的 `platform_id` 相同时按 `kind` 区分，各自对应正确的会话；配置中三项完全相同的重复会话被拒绝；淡化状态随导出导入保留；合并取较晚时间和较长半衰期；回想进度不进导出包。来源会话按平台身份对应：配置中改了逻辑 ID、群号不变时（本地和导入都覆盖）自动对应；逻辑 ID 相同、群号不同时不对应，包内记录不出现在配置中的那个群；找不到时只对内可见、按登记类别淡化、`status` 提示，配置加入该群号后自动恢复；本地与导入的同名不同群记录互不影响；对应不产生修订；旧格式包和无法得知身份的来源只对内可见且不淡化；再次导出时登记内容不丢失；更换平台插件时不自动对应。
14. **O1、O2**：投影读取出错时只跳过记忆段；守卫读取出错时按命中处理；重复合并同一个包保留上次的选择。
15. **规则**：本体规则包含第 7 节新增的条目，主人私聊和群聊的模型请求都有回归。
16. **私聊经历在群里**：`relationship` 的私聊记忆在其他群可见、`private` 的不可见；主人用 `replaces` 改可见等级后投影随之变化；群里主人说起而找不到时，模型请求包含"不当面否认"规则，群友说起时仍是 L6 规则。
17. **回想模型**：未配置 `recollect.model` 时回想使用当前聊天模型；更换聊天模型配置后回想随之更换；配置后使用指定模型。
18. **停用回想**：停用时取消进行中的回想且不写入；重新启用后停用期间的消息和未完成的窗口都不补做，`status` 显示跳过的段数。

### B1 画图能力插件 `image-gen`

画图是独立的能力插件，与平台插件之间没有任何依赖。

**本体补充**（Issue #83）：插件要读取 API 密钥、要有真实的网络访问，这两项现在都还没有。B1 先按 [runtime-services-spec](architecture/runtime-services-spec.md) 第 1、3 节和 [ADR 0031](adr/0031-plugin-credentials.md) 实现它们，并通过测试，再写插件。

**范围**
1. **工具**：`draw_image`（根据描述生成）和 `edit_image`（修改本会话上一张生成的图）。插件在自己的存储里按会话记录最近几次生成的结果。两个工具都标为 `heavy`，走 ⏳✅❌ 回应。
2. **后端适配层**：插件内部定义统一的后端接口（生成、修改、错误码），错误码包括 `content_refused`、`rate_limited`、`transient`、`quota_exceeded`、`invalid_request`。本里程碑只实现一个真实后端：OpenAI 图像接口，通过 `ctx.http` 调用，图片经 `ctx.asset_writer` 写入资产库后作为 `ToolResult.assets` 返回。
3. **后端顺序与回退**：配置里按顺序列出后端。某个后端返回 `content_refused` 时，只有配置 `fallback_on_refusal: true`（默认 `false`）才尝试下一个后端。本里程碑只用假后端测试这套回退逻辑。回退只换图像模型，本体的边界规则照常生效。
4. **配置与费用**：模型名是必填配置，不设默认值，由用户选定。API 密钥通过 `ctx.credentials` 读取，插件配置里只写凭据引用名。不做每日次数限制，费用上限由平台侧设置（runtime-services-spec §2）；平台返回额度用完时映射为 `quota_exceeded`，如实告诉模型。
5. **测试**：假 HTTP 后端覆盖成功、各种错误码、超时、取消和超大返回。另有一条离线端到端测试：假模型调用 `draw_image`，经 `fake-channel` 发出图片，账本状态和表情回应都正确。

**不做**：本地生图后端（以后作为扩展）；以用户发来的图片或旧消息里的图片为底图（依赖入站媒体下载，以后再做）；图片内容审核（出站检查不检查图片内容，见 agent-spec）。

**验收**
- tool 扩展点的契约测试通过，包括幂等键和取消。
- 后端错误码的映射，以及回退开和关两种情况，都有测试。
- 代码中没有按关键词或正则判断"是否要画图"的路径；是否画图只取决于模型发出的工具调用。
- 密钥不出现在日志、账本和错误信息中；双平台 CI 通过；真实生图调用次数为 0。

### B2 QQ 平台插件精简版 `qq-onebot`

**SDK 补充**：现有 `ctx` 只有一次性 HTTP 请求，无法维持长连接。按 [ADR 0030](adr/0030-websocket-client.md) 增加 `ctx.websocket` WebSocket 客户端（需要 `network` 权限），按 runtime-services-spec §4 接好生产后端，并实现 §1.5 的账号密钥读取。先完成并通过契约测试，再写插件。

**范围**
1. **连接**：使用正向 WebSocket，由 Clytie 主动连接协议端的地址（来自配置）。令牌放在 Authorization 请求头里以 Bearer 方式发送，令牌放在绑定账号的 `accounts.<ref>.secret` 文件里，用 `ctx.credentials.account_secret()` 读取（runtime-services-spec §1.5），不写进配置正文和日志。预期账号用 `ctx.identity.self_account()` 读取（ADR 0032）；未绑定账号时 `start` 抛出 `PluginUnavailable("auth_invalid")`。连上后用 `get_login_info` 取协议端登录的账号，与预期账号按字符串比较；不一致就断开，状态为 `auth_invalid`，在重启前不再重连。之后每个事件的 `self_id` 也要等于预期账号，不等的事件丢弃并计数。断线后按配置的退避间隔重连（默认 1、2、4、8、16、30 秒），用完后按最后一个间隔一直重试，直到连上或插件停止；`auth_invalid` 不重连。确定没有发出的消息和表情回应，收据为 `failed` 加 `transient`，由本体有限重发。
2. **入站**：私聊和群聊的 message 事件转成 `EventEnvelope`，`event_id = "{channel_id}:{message_id}"`。发送者等于预期账号的消息不进入对话。消息段映射：`text`→text，`at`→mention（`qq` 等于预期账号时 `is_self`），`image`/`record`/`video`/`file`→对应类型（只给 `raw_ref`，不下载），`reply`→quote，`face`/`mface`→sticker，其余→unknown（保留 `raw_type`）。`file` 和 `mface` 不是标准消息段，按兼容契约第 3 节处理。账号和会话的映射只用 `ctx.identity`。入站队列有上限；溢出的事件被丢弃，但必须记告警和计数，并在状态中可见。
3. **出站**：用 `send_private_msg` 或 `send_group_msg` 发送消息段数组，用 `echo` 对应请求和回复。收据按 kernel-spec §5–§6 判定：
   - `status=ok` 且带 `message_id`：`sent`；
   - 协议端明确返回失败：`failed`。只有配置 `retcode_classes` 里列出的返回码算 `rate_limited` 或 `transient`，其余都是永久错误（默认配置为空，见 [qq-onebot 兼容契约](plugins/qq-onebot-compat.md) 第 5 节）；
   - 超时、断线、`echo` 对不上、成功回复里没有 `message_id`：`unknown`，不重发。

   超出 `media_limits` 的产物由插件拒绝，记为 `failed`。
4. **表情回应**：用 `set_msg_emoji_like` 映射 👌⏳✅❌，表情编号来自配置。请求字段、"不支持"的判定和降级规则见兼容契约第 2 节；不报错退出。
5. **状态**：`state()` 报告 online、connecting、offline、auth_invalid 或 unknown。协议端的心跳超时视为假在线，状态改为 unknown，并主动断开重连。
6. **测试**：手写录制格式的假事件，覆盖每种消息段、私聊、群聊、自身消息和畸形数据。另用一个假协议端，在 `127.0.0.1` 上跑真实的 WebSocket 往返，不访问外网。

**不做**（以后再补）：入站媒体下载进资产库；掉线和登录失效时提醒 owner；反向 WebSocket 和 HTTP 连接方式；合并转发；拉取历史消息、群成员列表、引用原文；登录、二维码、协议端进程管理等协议端专属的管理接口；官方 QQ 机器人；一个插件实例对应多个账号。

**验收**
- `ctx.websocket` 的契约测试通过，ADR 0030 与 sdk-spec 同步。
- `self_account()` 的契约测试通过（ADR 0032）；账号不一致、事件 `self_id` 不一致、自身消息和 @ 自己各有测试。
- channel 扩展点的契约测试全部通过。
- 每种消息段的入站和出站映射都有测试。
- 兼容契约第 6 节列出的测试都有。
- 收据三种结果各有测试，包括超时、断线、`echo` 错配和迟到回复。
- 账号不一致、令牌缺失、心跳超时、重连上限各有测试。
- 插件只 import `clytie.sdk`；双平台 CI 通过；真实平台连接和发送次数为 0。

### B3a 模型插件 `openai-api`

普通模型插件（`agent_type = false`），使用本体现有的工具循环（agent-spec），不需要 MCP。

**范围**

### B3c `openai-api` 的 Responses 模式（草案，2026-11-16）

第一次真实测试中，聊天模型在 Chat Completions 接口下带工具调用时返回 400（`param=reasoning_effort`）；关闭推理或改用 Responses 接口都能成功。用户要求效果优先，不用关闭推理换取可用。openai-api 增加 `api: responses` 和可选的 `reasoning_effort`，推理内容在工具循环中保持连续，只改插件，不改本体和 SDK。范围、不做项和验收见 [openai-api-responses](plugins/openai-api-responses.md)。

### B3d 上下文中的非文字占位（草案，2026-11-16）

图片、表情包、@ 等非文字消息段在交给模型的上下文中用占位文字表示，不再被当成空消息；出站检查、快速取消和记忆检索不受影响。规则见 [agent-spec](architecture/agent-spec.md) §4.4。不下载入站图片（Issue #101 第 2 项另行决定）。

**验收**
- 占位表的每一行都有测试，覆盖聊天记录、本次消息和被引用原文，入站和出站都覆盖。
- 出站检查、快速取消识别和记忆检索查询的输入与修改前相同。
- 占位中不出现平台账号、逻辑 ID 和 `raw_ref`；双平台 CI 通过。

### B2b 任务表情完善（草案，2026-11-17）

真实测试发现三个问题：QQ 上状态表情会叠加；画图被拒绝时仍显示"完成"；表情编号只能从 QQ 实际获取。

1. **只显示一个状态表情**：qq-onebot 增加 `react_remove`，用 `set: false` 撤掉旧表情（qq-onebot-compat §2.1）。本体沿用 kernel-spec §13.5 的"先撤旧的再加新的"，不用改。
2. **工具失败显示失败**：kernel-spec §13.5 新增的规则，最后一次 `heavy` 工具调用失败并且没有成功重试时，最终表情用"失败"。
3. **表情编号采集**：CLI `clytie emoji capture`：启动后在限定时间内（默认 3 分钟），按顺序记录 owner 在 QQ 中添加的四个表情，显示给用户确认后再写入配置（经 API 写回，保留配置历史）。只使用 qq-onebot-compat §2.2 的通知。WebUI 版放在阶段三。
4. **真实测试观察脚本**：任意一步失败（包括工具失败）立即停止，不等文字回复。B5 完成后由冒烟测试工具代替。

**验收**
- compat §6 新增的撤销测试；本体在 `supports_react_remove` 为真时先撤后加的现有测试仍通过。
- 失败判定：画图被拒、`denied`、超时各一条，最终表情为"失败"；之后重试成功时为"完成"；没有 `heavy` 调用的任务不受影响。
- 采集：只接受 owner 的回应；超时、不足四个、协议端不支持时如实报告且不写配置；用户不确认就不写配置。
- 双平台 CI 通过；真实平台连接次数为 0。

### B4b owner 在场判断与工具使用范围（草案，2026-11-17）

- `owner_present` 准入模式：平台插件按可选能力回答成员查询，qq-onebot 用 OneBot v11 标准接口实现。范围和验收见 [admission-spec](architecture/admission-spec.md) §5、§7。
- `tool_scopes`：按工具设置谁在什么会话能用。私聊只有 owner 能用画图；群里默认所有人可用，可以排除个别人。范围和验收见 [tool-scopes-spec](architecture/tool-scopes-spec.md)。

### B5 真实冒烟测试工具（草案，2026-11-17，用户已确认方向）

用户手动测试只适合每次一两条。冒烟测试工具用来在上线前和改动后批量做真实测试。

- 一个专门的测试 QQ 账号（由用户准备，不是伴侣账号，也不是 owner 主号），通过单独的协议端连接。
- 按用户确认过的固定用例清单，向测试会话发送消息，例如用几种不同说法请求画图（L1）。测试方不调用模型，结果可复现。
- 通过本机 API 读取被测伴侣的收据、状态表情、用量和耗时，生成报告；任意一步失败立即停止。
- 每次运行需要用户当次同意，只发往测试会话，并且先通过成员检查（AGENTS.md 3.2）。
- 开始前先补规格；测试账号在测试会话中按普通成员登记，不登记为同部署的伴侣。
- 规格：`docs/architecture/smoke-spec.md`（草案，2026-11-17）。

### B6 看图（用户已确认，2026-11-19）

收到的图片交给模型看。看图是本体的基础能力：平台插件负责取图，本体负责准入、存储、场景可见性和交给模型的规则，模型插件负责格式转换。效果优先，不为节省费用少给图（用户已确认，2026-11-19）。决定 Issue #101 第 2 项。规格：`docs/architecture/vision-spec.md`。

- 场景：所有已准入的会话（用户已确认，2026-11-19）。
- 不做：认出自己的形象（Issue #34）、图片记忆、用别人发的图改图、表情包。后续顺序见 vision-spec §9（用户要求先做好规划，2026-11-19）。
- 截图里的文字只当图片内容，写进验收（用户已确认，2026-11-19）。

### V2 认出自己的形象（草案，2026-11-20，用户已确认方向）

看到画她的图时能认出是自己，拿不准时不乱认。对应 Issue #34。规格：`docs/architecture/appearance-spec.md`。

- 形象资料可选，什么都不放也能用；本体只检查格式、大小和张数，不按画面内容拦截（用户已确认，2026-11-20）。
- 按证据和场合判断是不是自己，不按资料多少分档；修改形象不写记忆；保存后自动自检一次（用户已确认，2026-11-20）。
- 不做：让她画形象后挑选为参考图（V2b）、在聊天里修改形象、存下画她的图。
- 规模预估：2.5–3.5 天，另加一次真实抽检。

### B7 群聊行为：说话时机与回复形态（已完成，2026-11-22）

她在群里不只是被 @ 才说话：自然接话、聊多了会累、没人理先安静；回复像平常发消息一样分几句说。规格：`docs/architecture/chat-behavior-spec.md`，决策记录 ADR 0035。

- 两个官方行为插件 `chat-timing`、`reply-form`，和平台无关；本体补充被叫到的标记、轻量判断和群聊安全带（用户已确认，2026-11-22）。
- 自然接话默认先用规则筛选，再用同一个模型轻量判断；疲劳看发言比例不看次数；被 @、回复她的消息一定回应；安全带默认 30 分钟 200 次，可以调、不能关，每次触发都提示（用户已确认，2026-11-22）。
- 不做：多位伴侣同群协调、卡片和合并转发、模拟打字、发表情包、安全带手动解除。
- 规模预估：5–6 天，另加一次真实冒烟测试。
- 补测后追加（用户已确认，2026-11-22）：被叫到和私聊时边等边写，等待期间先写回复，同一个人又发消息就重写（规格第 3.5 节，SDK 0.17）；正式回复的用量审计补上模型耗时和缓存命中；内测阶段样本太少，不设观察期。约 2–3 天，另加一次补测。
- 结果（2026-11-22）：真实补测四个用例全部通过。被叫到时，从最后一条消息到开始回复的时间从 8.8–16.5 秒降到 5.5–8.5 秒；剩下的基本是模型本身的耗时。

### B7d 接着聊（已完成）

外部群开放后发现：大家接着她的话聊时，大多不 @ 也不引用，她聊几句就断了。规格：chat-behavior-spec §5.3a，决策记录 ADR 0044。

- 她在群里说完话后 2 分钟内，群里任何人的消息都直接交给轻量判断，不过随机筛选，只看疲劳；判断时告诉她"这条可能在接你的话"。
- 窗口内最多每 10 秒判断一次。判断失败时，主人的消息回应，其他人的不回。
- 被 @、回复她、叫名字的处理不变；疲劳、群聊安全带照旧。
- SDK 0.23：判断事实新增 `follow_up`，有默认值。
- 验收：chat-behavior-spec §10 第 14、15 项。上线后由用户在平时使用的群里观察。
- 规模预估：约 1–1.5 天。
- 结果：PR #229 合并（tag `b7d`）。审查时补充：主人的消息另算判断间隔，`rules` 模式下别人的消息不占用间隔（PR #230）。实现时澄清了三点：拆开发的回复每条都续期窗口；按 `focus` 记她回应过的人；每个群缓存 50 条。上线后第一个小时，群里 50 条消息，判断 15 次，回复 12 次。

### B8 主动私聊与睡眠作息（草案，2026-11-22，用户已确认方向）

她会主动找主人：早安、好久没聊、节日，碰到想分享的事一口气说好几句，有时画一张图发过去；她也有自己的作息。规格：`docs/architecture/proactive-spec.md`，决策记录 ADR 0036。

- 顺序：B8a 主动私聊 → B9 内容来源 → B8b 睡眠作息（用户 2026-11-22 确认）。
- B8a：
  - 行为插件 `proactive-chat`，只找主人，只在私聊；
  - 主动开口可以使用能力，按配置清单和每天的次数提供，解决 Issue #23；
  - 本体的"暂停主动聊天"开关；SDK 0.18。
- 节奏（用户 2026-11-22 确认）：好久没聊按 2–3 小时随机；一次开口最多 6 条；两次开口至少隔 30 分钟，新鲜事不受限；主人没回时等待逐步拉长；主人 00:00–08:00 休息时不打扰。
- 验收：离线测试，加上一份三天的离线模拟时间线。合并后经用户同意上线，不设试用期，有问题再反馈修改。
- B8b 的方向已确认，见规格第 12 节，开始前补全规格。
- 不做：在群里主动说话、"约好的事回头问"、两位伴侣之间的作息。发 QQ 空间、推特动态以后单独做（规格第 13 节）。
- 规模预估：B8a 3–4 天；B8b 4–5 天。

### B9 内容来源（草案，2026-11-23，用户已确认方向）

她能查资料、看懂别人发的链接；有值得说的科技和 AI 消息时主动告诉主人。规格：`docs/architecture/content-spec.md`，决策记录 ADR 0037。

- B9a 搜索和读网页：能力插件 `web-tools`；搜索先做适配层，本期只接与聊天模型同一家的 OpenAI 联网搜索，中文来源保留；查资料不升级为任务；读网页只访问公网；读过的资料 15 分钟内附全文，之后可以取回。群友也能用。约 4–5 天，另加一次极小的真实检查。
- B9b 订阅与主动分享：只要科技和 AI 内容，来源以 Hugging Face、GitHub、arXiv、官方博客、英文科技媒体、Hacker News 为主；每天早上一次每日一报，大新闻马上说、不设每天上限，半夜按主人醒没醒决定（用户 2026-11-24 确认）。约 5 天。
- 看视频单独立项：B站、YouTube 和群里的视频，本机下载、转写和抽帧，可选接入能直接看视频的模型。
- 不做：读 PDF、需要登录的网站、聊天记录里的链接编号。

### B3b 模型插件 `codex-cli`（范围待定）

Codex CLI 属于 Agent 类模型：它自己跑工具循环，通过 MCP 调用工具。agent-spec 规定 A3.2 不支持这类模型，MCP 的接入留到阶段二再设计。B3b 开始前，先由设计审查会话起草"本体如何通过 MCP 向 Agent 类模型提供工具，同时保留权限、额度、账本和取消"的规格，用户确认后再定范围和规模。能力插件对两个模型入口看到的是同一套工具，不需要修改。

以后如果需要"Codex 额度用完后改走 API"，做成显式的回退开关：默认关闭，每次切换都提醒 owner。不在本段实现。

### 额度感知（B3b 之后，范围待定，用户已确认方向）

- **问了能答**：模型能拿到准确的剩余额度和重置时间时，把它们写进每次调用的能力状态（L3），有人问起时如实回答；拿不到时就说不确定，不编造数字。
- **快用完时提醒**：剩余额度跌过阈值或用完时，伴侣用自己的语气私聊 owner，同一个额度周期内每个阈值只提醒一次；走主动消息的话题方式，不在群里说。
- **开始前先查证**：Codex CLI 和 OpenAI API 能否让程序读取剩余额度，查清后再定范围；拿不到数据的入口只做"用完时如实告知"。

### C 漫画工具与漫画简报（已完成，2026-11-27）

她能把一件事画成多格漫画，自己当主角，需要时让角色表里的角色出场；每日一报可以做成漫画。规格：`docs/architecture/comic-spec.md`，决策记录 ADR 0039、0040。

- C1 漫画工具：能力插件 `comic-maker`（`draw_comic`、角色表、字体库、页眉页脚）；`image-gen` 新增服务 `image.render`；本体新增 `appearance.read`、能力之间服务调用的上下文与资产传递，以及插件导入文件的通道和插件路由的确认；SDK 0.20。约 7–9 天，另加一次真实检查。
- C2 漫画简报：每日一报满足条件时提示她做成漫画；大新闻仍然只发文字。另外补上工具说明中的页数和格数；一条消息放多张图（SDK 0.21，ADR 0040）。约 3 天。
- 主角始终是本伴侣自己的形象资料，换人设就跟着换；角色表和参考图由用户提供，不限于私聊；不画真人长相；字体由用户导入，仓库不内置（用户 2026-11-25 确认）。
- 不做：看图核对和错字重画（等 V6）、程序排对话框、两位伴侣同框、发到动态。

### 说话风格（范围待定，2026-11-24 记录，用户暂不决定）

B9a 上线检查时，她转述网页的回复像在念说明书。用户希望以后让她说话更像真人，B9 完成后再定范围。设计审查会话提出的方向：

- **转述规则**：转述资料时用自己的话、挑重点、口语化，不照搬原文和书面语。改动很小。
- **说话样例**：人设中加入不同场合的说话样例和反例，本体按当前场合挑几条放进上下文。样例由主人编写，放在实例的人设目录中，不进仓库。
- **主人纠正**：主人说"这句太像机器人了"时，她记下这条反馈，以后避免。
- **表达学习**：从登记过的群和主人私聊中学习"什么情况下大家怎么说"，只学说法不学内容；复用 A3.4 学习黑话的机制，在某个群学到的说法只在那个群用，私聊的说法不带进群里。思路参考 MaiBot 的表达学习，只借鉴思路。
- 不建议使用外部语料，版权有问题，口吻也不是她自己的。旧系统的聊天记录等主人正式投入、搬旧记忆时再考虑。
- 待定：做哪几层、先后顺序、学习来源和使用范围，以及和看视频的先后。

### B10 平台离线提醒（已完成，2026-11-26）

QQ 在 NapCat 中掉线后，平台状态只是"离线"，守护进程不会通知主人；实例也没有配置通知插件，已有的提醒同样送不到。所以掉线几个小时都没人发现。规格：supervisor-spec §5.3–5.6，决策记录 ADR 0041。

- 启用桌面通知：守护进程已有的提醒（登录失效、额度用完、停止重启、被阻止启动、强制终止、群聊安全带等）都能送到主人（用户 2026-11-26 确认）。
- 平台不在线连续 15 分钟时提醒；一直没恢复时每 3 小时再提醒；恢复在线时不提醒；启动后一直没连上也算；睡眠后唤醒不误报（用户 2026-11-26 确认）。
- 新增配置 `notify.mute`，不弹出的提醒种类。实例关掉备份密钥的提醒，因为备份以后要重构（用户 2026-11-26 说明）。群聊安全带的提醒不能关。
- 新增测试通知 `clytie supervisor notify-test`；`desktop-notifier` 改用 Windows 已注册的应用标识。
- 模型偶尔调用失败不另外提醒：平台通着时，她会在聊天里回失败回应。
- 不做：手机上的提醒（邮件、推送，见下一节）、恢复提醒、平台恢复后她在聊天里说明、自动重新登录。
- 验收：离线测试（MockClock、假通知后端）。合并后经用户同意部署，弹一次测试通知，由主人确认看到了。
- 规模预估：约 1.5 天。

### B11 掉线期间的消息补收（已完成，2026-11-28）

QQ 掉线或伴侣停机期间，别人发来的消息恢复后收不到，她也不知道自己错过了消息（Issue #210）。规格：catch-up-spec，决策记录 ADR 0042。

- 恢复在线、稳定 10 秒后补收，伴侣启动后第一次连上也补。只看账本的防重表判断是否看过，反复掉线、重启不会重复处理。
- 主人私聊：最多 24 小时、50 条，作为一批，她回应一次。
- 登记的群：最多往回读 200 条，没看过的都记为聊天记录，话题保持连续；只回应最近叫过她的 3 个人，每人各回一次（用户 2026-11-27 确认）。
- 回应按人设，不用固定的说法，不编造当时在做什么（用户 2026-11-27 确认）。
- 补收做不到、掉线超过 15 分钟时，她给主人说一句（用户 2026-11-27 确认）。
- SDK 0.22：平台插件可选的 `history()`。qq-onebot 用标准之外的接口，真实核对确认消息编号一致后才在部署中打开。
- 不做：她自己没发出去的消息（Issue #214）；陌生人私聊、未登记的群、其他私聊。
- 验收：catch-up-spec §13 的离线测试；合并后经用户同意按 §14 在测试群做一次真实核对。
- 规模预估：约 3 天，排在 Issue #212 的修复合并之后。
- 结果：PR #218 合并（tag `b11`）。审查时补充了两条规格：补收起点按恢复前的数据算（PR #217）；没补完的恢复时刻要保留，实时消息按收到的时间排序（PR #219）。2026-11-28 真实核对：消息编号一致；翻页方向和契约原先写的相反，修订兼容契约 §7 后由 PR #221 修正；测试群离线时 @ 她，启动后只回应一次，再次重启不重复回应。

### B11b 没发出去的消息和较早的群消息（已完成，2026-11-28）

平台掉线时，她要发的消息发不出去（Issue #214）。规格：catch-up-spec §16，决策记录 ADR 0043。

- 平台不在线时不主动开口：按"会话正忙"处理，不调用模型。恢复后到点的话题照常说；时间段不因掉线延长，早安过了就不说，每日一报到 14:00、节日到 20:00。
- 回应别人的消息因为平台断线一条都没发出去时，恢复后重新交给她，她按现在的情况重新写，每条最多一次。发出了一部分、结果不明、被平台拒绝、重启时中断、执行过能力的，以及群里没人叫她的，都不重新回。
- 主人私聊：和补收到的消息合成一批，她回应一次，24 小时以内的都回。
- 群：参加 B11"最近 3 个人、最多 10 条"的挑选。超过 60 分钟的先由轻量判断决定还要不要回，判断失败时不回；B11 补收到的较早的叫她的消息也一样（用户 2026-11-28 确认）。
- 不做：发送结果不明的消息仍不补发。
- 验收：catch-up-spec §16.6 的离线测试。
- 规模预估：约 2–3 天。
- 结果：PR #225 合并（tag `b11b`），2026-11-28 部署，使用默认配置。实现时补充了账本格式：新记录用原记录 `trace_id` 的列表，同一事务标记原记录（PR #224）。审查时补充了两条规格（PR #226）：平台插件没有实现 `state()` 时照常主动开口；一批里只有部分消息只回表情时，照常回应整批。两次恢复重叠时，后一批的新消息可能被忽略，这种情况很少见，暂不处理。

### 提醒的后续完善（范围待定，2026-11-26 记录）

B10 只提供 Windows 桌面通知。部署在服务器、NAS、Docker 或云主机上时，旁边没有屏幕；主人出门时，桌面通知也看不到。提醒的判断在本体（守护进程），在各个系统上都一样；缺的是送达方式，也就是 `notifier` 插件。

用户 2026-11-26 决定：先完善主体功能，再做这部分。

- **手机提醒插件**：从邮件、微信推送服务、Bark（只支持 iPhone）中选一种，由用户决定。还要定：
  - 提醒会经过第三方服务，正文中的伴侣 id 换成主人设置的别名，不发出真实名字；
  - 全部静默时是否照发。设计审查会话建议照发：这是发给主人的系统提醒，不是她在说话；
  - 推送服务的凭据按插件凭据保存（runtime-services-spec）。
- `desktop-notifier` 不在 Windows 上运行时，明确报"不支持这个系统"，不返回"结果未知"。
- `supervisor status` 中的时间按实例时区显示，不显示 UTC；重复提醒中的离线时长写成"X 小时 Y 分钟"。
- Linux 桌面通知（`notify-send`）等有人在 Linux 桌面上使用时再做。
- 不做：机器关机或断网时的提醒，这只能靠外部的监控服务。
