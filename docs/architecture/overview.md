# 架构总览

## 1. 设计原则

1. **本体小而稳**：本体只做所有伴侣都需要、并且关系到安全和数据正确性的事。其余一切都是插件。
2. **功能可替换**：当前列出的功能只是预设。新增、替换、删除一个功能，只需要新增或停用插件，不改本体。
3. **扩展点优先**：插件通过声明的扩展点接入（见 `plugins.md`）；扩展点是架构的核心资产，需要稳定、版本化、有契约测试。
4. **伴侣即配置**：一个伴侣 = 人设 + 记忆库 + 模型插件 + 平台账号 + 启用的插件及其配置。代码中不存在"某个具体伴侣"。
5. **数据与代码分离**：代码在仓库，数据在实例目录 `CLYTIE_HOME`。迁移 = 代码 + 实例目录备份。
6. **安全不可卸载**：权限、隐私投影、关系边界、出站检查在本体中，任何插件都无法绕过。
7. **可离线验证**：每个接口都有假实现和契约测试；模拟时钟驱动所有与时间有关的逻辑。

## 2. 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 界面层   WebUI、CLI（只调用 API）                                │
├──────────────────────────────────────────────────────────────┤
│ API 层   本机 HTTP API（127.0.0.1）                             │
├──────────────────────────────────────────────────────────────┤
│ 插件层   能力 / 行为 / 平台 / 模型 / 记忆扩展 / 导入器 ……           │
│          只依赖 clytie.sdk                                     │
├──────────────────────────────────────────────────────────────┤
│ SDK 层   clytie.sdk：接口、数据类型、事件、扩展点注册               │
├──────────────────────────────────────────────────────────────┤
│ 本体     kernel  agent  memory  persona  boundary               │
│          plugin_host  scheduler  supervisor  config  assets     │
└──────────────────────────────────────────────────────────────┘
```

依赖方向只能从上往下；本体不依赖任何具体插件（只依赖 SDK 中定义的接口）。

## 3. 本体模块

| 模块 | 职责 |
|---|---|
| `kernel` | 事件信封、身份解析、防重、会话排队（主人优先）、统一任务账本、交付与收据、事件总线 |
| `agent` | 上下文装配、模型调用与工具循环、能力状态注入 |
| `memory` | 记忆存储、可见等级投影、检索编排、修订与撤销、导入导出框架 |
| `persona` | 按伴侣和场景加载人设文件并分层组合 |
| `boundary` | 权限、关系边界保护、保障模式、输入过滤、出站检查 |
| `plugin_host` | 插件发现、清单校验、依赖解析、扩展点注册与分发、配置、启停、隔离 |
| `scheduler` | 统一的定时器和模拟时钟；插件的定时任务都由它驱动 |
| `config` | 分层配置加载（默认值 → 插件默认 → 实例配置 → 伴侣配置）与 Schema 校验 |
| `assets` | 内容哈希资产库、平台格式转换 |
| `supervisor` | 进程管理、健康检查、重启、通知、维护任务 |
| `api` / `webui` / `cli` | 管理接口与界面外壳 |

## 4. 运行时结构

```
supervisor（单实例）
├─ api 服务
├─ 伴侣进程 A ──┐
├─ 伴侣进程 B ──┼── 本机伴侣通道（任务委托、状态订阅、同群协调）
└─ 外部组件（Docker：平台网关、页面渲染等）
```

- 每个伴侣一个进程，加载本体 + 该伴侣启用的插件。一个伴侣崩溃不影响其他伴侣。
- 伴侣之间不共享记忆库；只通过伴侣通道交换必要材料。

## 5. 消息流程

```
平台插件 ─► EventEnvelope
  kernel：身份解析 → 防重 → 输入过滤 → 消息合并 → 会话排队
        → [扩展点 before_attention / attention] → 边界检查 → 写入账本
  agent：上下文装配（人设 + 记忆投影 + 预算 + 能力状态 + 插件段落）
        → 模型插件 → 模型选择工具 → 权限/额度把关 → 能力插件执行 → 结果回到模型
        → 回复 → [扩展点 after_generation] → 出站检查
  kernel：[扩展点 before_send] → 交付 → 收据写入账本 → 事件 task_completed
```

- 能力选择由模型在同一次调用中用自然语言判断；程序只保留"取消/停止"一条快速路径。
- 不能用的能力及原因（权限、保障模式、维护中）每次注入上下文，避免模型编造理由。

## 7. 演进方式

- 新平台：新增平台插件。新模型：新增模型插件。新功能：新增能力或行为插件。都不改本体。
- 本体需要变化时：先写 ADR，说明为什么现有扩展点不够；SDK 按 `sdk.md` 的版本策略升级。
