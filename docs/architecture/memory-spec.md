# 记忆核心实现规格（A3.3：存储、投影、当场记、检索、导入导出）

本文件是 A3.3 的实现契约，细化 `design/memory.md` 和 `data-and-backup.md` 第 2、3 节。标注"用户已确认"的条目不能在实现中改变；其余条目实现时如有歧义，先只读询问 Claude，涉及需求或隐私的登记 Issue 并停下。

目标（用户已确认）：记忆要做到最自然的呈现。她像人一样记事：要紧的事当场记住，过后回想整理（A3.4），被纠正就改，久了的小事慢慢淡（A3.4），不记得就直说。

## 0. 范围与拆分（用户已确认）

| 里程碑 | 内容 |
|---|---|
| A3.3 记忆核心（本文件） | 存储、修订与撤销、可见等级投影、当场记、可信程度、语义 + 关键词检索、上下文接入、私密记忆的出站检查、加密导入导出、L6 |
| A3.4 回想与印象 | 对话结束后的回想整理（经历）、群里看到的和主人有关的事、群友印象、软遗忘与"想起即加深" |

- 代码在 `src/clytie/memory/`，属于本体，不能停用。检索器、向量模型、重排模型、导入器是扩展（sdk-spec §7）。
- 每个伴侣一个库：`companions/<cid>/memory/memory.sqlite3`，SQLite 是唯一事实来源。
- 所有测试使用临时实例目录、假向量模型、假模型和虚构数据，**不下载任何模型、不读取真实记忆库**。

## 1. 存储

### 1.1 记录

字段沿用 sdk-spec §1.7 `MemoryRecord`，新增两项，**都由本体填写**，模型和插件都不能指定：

| 字段 | 取值 | 说明 |
|---|---|---|
| `basis` | `owner_confirmed` \| `owner_stated` \| `observed` | 可信程度（第 2.3 节） |
| `origin_conversation_id` | 会话逻辑 ID 或 `null` | 可信的来源会话（第 3.2 节），随修订保存和导出 |

- `write_mode = confirmed` 当且仅当 `basis = owner_confirmed`。
- 记忆库中这两项必填（`origin_conversation_id` 可以是 `null`）。SDK 类型中为可选字段，缺失时按 `write_mode` 推导 `basis`（`confirmed` → `owner_confirmed`，`auto` → `observed`），`origin_conversation_id` 视为 `null`；这只用于读取旧格式的对象。任何写入入口都忽略外部传入的 `basis`、`write_mode`、`origin_conversation_id`。写入 CHANGELOG。
- `source_type`、`source_ref`、`scope` 保留为说明字段：本体写入时自己填写；插件写入时 `source_type` 由宿主按绑定场景填写，插件传入的值被忽略。投影只看第 3 节的规则，不信任说明字段。

### 1.1a 伴侣身份标识（用户已确认）

- 配置里的伴侣编号（`companions/<编号>/`）是用户起的名字，只用来区分目录和命令，**不作为身份依据**。
- **她的身份从第一条记忆开始**：记忆库建立时没有身份；第一次写入记录或第一次导入时，本体生成一个随机的 `companion_uid`（32 位十六进制），写进记忆库本身，之后永不改变，不随配置里的编号改名而变。
- **空库**的定义：还没有 `companion_uid`，也就是从未写入过任何记录、也从未导入过。写过的记录即使后来撤销，库也不再是空库。普通的初始化审计不影响。
- 导出包的清单带上 `companion_uid`；整体搬家时它随记忆库一起迁移。"是不是她的记忆"按这个标识判断（第 9.2 节）。
- 这个标识只在导入时使用，不改变她的任何行为。导入事件只写审计，**不额外生成**关于"导入过""搬过家"的记忆；导入的记录本身照常写入。

### 1.2 表

具体表结构由实现决定并写 ADR，逻辑上至少包含：

- **记录表**：每条记录的当前版本。
- **修订表**：每次写入、修订、撤销都追加一行（记录 ID、修订号、完整内容、内容指纹、上一版本的指纹、时间、操作者、来源追踪号、导入编号），只追加不修改。内容指纹是规范序列化后的哈希，用于导入时判断共同祖先（第 9.2 节）。
- **审计表**：导入、导出、撤销导入、检索器或向量模型不可用等事件。
- **关键词索引**：中文可用。"香菜""考试"这样的两字词必须能检索到；具体分词方式写进 ADR。
- **向量表**：`(record_id, revision, embedder_id, vector)`。向量属于派生数据，可以随时重建，不进入导出包。

### 1.3 修订与撤销

- 修订：`expected_revision` 必须等于当前修订号，否则返回 `RevisionConflict`。修订号加 1，旧版本保留在修订表里。
- 撤销：`retracted = true`，修订号加 1，记录本身保留。撤销后任何检索、投影、上下文都看不到它。
- 单条记录的恢复撤销、彻底删除不在 A3.3 范围（A4 的管理接口，或以后的 WebUI）。导入的 `restore` 和撤销导入把已撤销的记录改回有效，属于第 9 节规定的导入操作，不是单条恢复。彻底删除需要同时处理备份留存，不能把"隐藏"说成"擦除"。
- 去重（用户已确认）：
  - 只在**写入方本来就读得到**的有效记录中查重；读不到的记录当作不存在，另外新建一条。这样不会借查重泄露私密记录的存在、来源或时间。
  - 查重按 `kind`、`subject`、`visibility`、`origin_conversation_id` 分开，内容规范化（NFKC、去掉首尾空白）后完全相同才算重复。
  - 命中时不新建，返回已有的那条。主人在 `explicit = true` 时重复说了一条已有记录，本体把它升级为 `owner_confirmed`（新修订）。插件写入永远不升级。
  - 近似重复由她用"修订"处理，A3.4 的回想再负责合并。
- **可信程度只升不降**：聊天中的写入、修订和插件的任何操作都不会降低 `basis`。主人用 `explicit = false` 修订一条 `owner_confirmed` 记录时，仍保持 `owner_confirmed`。
  - 唯一的例外（用户已确认）：用户亲自确认执行的导入 `restore`、撤销导入、冲突中"使用包里的"或"改回导入前"、导入器的再次导入（第 9.4 节），按目标版本或本次选择写入 `basis`（`write_mode` 随之变化）。会降低可信程度的记录在计划中单独列出，整体确认一次即可。
- 插件只能修订或撤销 `basis = observed` 的记录（用户已确认）；对 `owner_confirmed`、`owner_stated` 的记录只读，修订或撤销时返回与"找不到记录"相同的错误。插件可以另外写一条新记录。她在聊天中用 `core_remember` 的 `replaces` 修订不受这条限制。

## 2. 当场记（用户已确认）

她在回复时觉得值得记，就当场记下，不需要主人说"记住"。

### 2.1 本体工具

在 agent-spec §3.3 的本体工具表中新增：

| 工具 | 何时提供 | 作用 |
|---|---|---|
| `core_remember` | 本批次的说话人是主人 | 记下一件事，或修订一条已有记忆 |
| `core_forget` | 本批次的说话人是主人 | 主人说"别再提了""那个记错了，删掉"时，撤销一条记忆 |
| `core_recall` | 本次模型调用允许使用工具时都提供 | 主动去回想：检索记忆和做过的任务（第 5 节） |

- "允许使用工具"沿用现有规则：主动消息的生成、模型不支持工具、工具轮数用完时 `tools` 为空，这时三个工具都不提供；记忆照常按第 5.1 节注入。
- 这三个工具与其他本体工具一样：不算能力调用，不升级记录为 task，不触发任务表情和任务单，调用和结果写入审计。
- 同一条记录（一次回复）里 `core_remember` 和 `core_forget` 合计最多调用 `memory.max_writes_per_record` 次（默认 5），超出时返回错误给模型，不写入。

### 2.2 `core_remember` 参数

| 参数 | 说明 |
|---|---|
| `kind` | `fact` \| `preference` \| `event` |
| `content` | 用自然的话写下这件事（她自己的措辞），不超过 300 字 |
| `visibility` | `private` \| `relationship` \| `public`。拿不准时填 `private`；缺省也是 `private`。replaces 修订 profile/jargon 的例外见 memory-recall-spec §4.1（Issue #43，用户已确认） |
| `explicit` | 布尔值：主人是否**明确**要她记住，或者正在纠正她的记忆 |
| `replaces` | 可选，上下文中的记忆编号 `[记忆N]`：表示这是对那条记忆的修订 |

- 本体填写：`subject`（主人的 `actor_id`）、`source_ref`（本记录追踪号）、`source_type`（场景为主人私聊时为 `private`；群聊中为 `owner_group_interaction`）、`basis`、`write_mode`、时间。
- `replaces` 指向的记忆必须在当前场景可见，否则返回"找不到这条记忆"，和不存在无法区分。修订使用注入时的修订号做 `expected_revision`，冲突时返回错误，由她决定是否重新回想后再试。
- 结果只告诉模型"记下了"或失败原因，不回显记录 ID。

### 2.2a `core_forget` 参数

| 参数 | 说明 |
|---|---|
| `target` | 上下文或 `core_recall` 结果中的记忆编号 `[记忆N]` |
| `reason` | 简短原因（写入修订，不交给其他模型调用） |

- 目标必须在当前场景可见；使用注入时的修订号做 `expected_revision`。
- 结果只有三种："已经不会再提了"、"找不到这条记忆"（包括不可见和不存在）、"记忆刚被改过，请重新回想"（冲突）。不回显真实 ID。
- 计入 `memory.max_writes_per_record`。

### 2.3 可信程度（用户已确认：程序区分，主人不需要额外动作）

| `basis` | 条件（全部由本体判断） | 作用 |
|---|---|---|
| `owner_confirmed` | 说话人经身份解析确为主人，并且 `explicit = true` | 最可信：核心记忆优先注入，检索时排在前面，永不淡化 |
| `owner_stated` | 说话人确为主人，`explicit = false` | 照常使用 |
| `observed` | 其他来源（插件写入、A3.4 的回想和印象） | 照常使用，排序在后 |

- 模型声称"主人确认过"不算数：`explicit = true` 但说话人不是主人时，工具本身就不会提供（第 2.1 节）。
- 账号映射决定身份，主人在私聊和群里都算（用户已确认）。
- 已有记录被主人明确再次确认时升级为 `owner_confirmed`；可信程度只升不降，例外见第 1.3 节。
- 她的猜测和印象（"感觉你最近很累"）不作为事实写入，这一点写进本体规则；程序无法核对，靠真实模型抽检。

### 2.4 不写入

写进本体规则，A3.3 中由工具提供条件保证一部分：
- 群友说的话：A3.3 不提供写入入口（说话人不是主人时没有 `core_remember`）。A3.4 起，别人说的关于主人的话也只能记成"某人说过某话"，不能变成关于主人的事实，也不能改变她对主人身份的认识。
- 主人说"不用记""别记这个"时不记；已经在本次记下的，用 `core_forget` 撤销。
- 转述、截图内容、她自己的推测。

### 2.5 写入失败

记忆写入失败（数据库错误、冲突）不影响回复：工具结果告诉模型失败，回复照常进行，记 WARN。不重试。

## 3. 可见等级投影

### 3.1 投影

所有对话和插件的读取都经过同一个本体函数 `project(scene, conversation_id)`，包括：上下文注入、`core_recall`、插件的记忆视图（替换 A2 的占位后端）、检索器的 `CandidateReader`、重排扩展。插件和扩展拿不到投影之外的记录。出站检查使用单独的守卫读取（第 7 节），不经过投影。

先按可见等级：

| 读取场景 | 可见等级 |
|---|---|
| `memory.private_scenes` 中的场景（默认只有主人私聊） | 全部 |
| 其他对内场景（`names.internal_scenes` 中、不在 `private_scenes` 中） | `public`、`relationship` |
| 对外场景（群聊等） | `public`、`relationship` |
| 陌生人私聊 | 无：不注入任何记忆，`core_recall` 返回空 |

再按来源会话（第 3.2 节），两条都满足才可见。

- 已撤销的记录在任何场景都不可见。

### 3.2 来源会话限制（用户已确认）

| 记录的 `origin_conversation_id` | 在哪些场景可见 |
|---|---|
| 主人私聊 | 按第 3.1 节的可见等级，各场景照常 |
| 某个群 | 这个群本身，以及**所有对内场景**（主人私聊、家庭群等）。其他普通群不可见 |
| `null`（没有绑定会话的插件写入、来源无法确认的导入记录） | 只在对内场景可见 |

- 在哪个群看到的事，只在那个群、私聊和家庭群这类"只有自家人"的场景里会想起，不带到别的群。对内场景按配置规则只有主人和本部署的伴侣，因此不受这条限制（用户已确认）。
- `origin_conversation_id` 由本体填写：本体工具用本批次所在会话；插件写入用宿主绑定的会话，没有绑定时为 `null`。插件无法把群来源伪装成私聊来源。
- 导入时来源会话的处理见第 9.2 节。
- 没有绑定场景的插件调用按 `public_group` 处理（沿用 sdk-spec §7.5 规则 3），这时没有来源群，因此群来源的记录全部不可见。

## 4. 检索（用户已确认：效果优先，语义 + 关键词，向量模型放在本机）

### 4.1 流程

1. **候选**：投影内的有效记录。
2. **两路召回**：
   - 关键词：第 1.2 节的索引。技术约定：查询含连续两个以上汉字时只用双字及以上中文词元匹配，单汉字查询仍可按单字；任务回想只匹配能力名、计划摘要、结果文本，不匹配元数据字段。
   - 语义：配置的 `embedder` 扩展把查询转成向量，和向量表中**同一 `embedder_id`** 的向量算余弦相似度。
3. **融合**：两路结果用倒数排名融合（RRF）合并。
4. **重排**（可选）：配置了 `memory.reranker` 时，用重排扩展对融合后的前 `memory.rerank_candidates`（默认 30）条重新打分。
5. **调整**：同等相关时 `owner_confirmed` > `owner_stated` > `observed`。A3.4 再加入淡化权重。
6. 取前 `memory.recall_limit`（默认 10）条。

排序与淡化的组合（用户已确认，Issue #37）：
- 第 4 步的候选段从**未乘淡化系数**的 RRF 顺序中取前 `memory.rerank_candidates` 条。
- 有重排时，候选段内**只使用重排的名次，不使用原始分数**：按重排分数从高到低排名，分数相同的共用名次（例如 1、2、2、4）；名次分为 `1 / (60 + 名次)`，再乘淡化系数（memory-recall-spec §4.2），按结果排序。重排分数可以是任意有限数（正负都可以）；返回长度不符、含 NaN 或无穷大时，本次视为重排不可用（第 4.2 节）。
- 候选段之外的记录按 RRF 分数 × 淡化系数排序，整体接在候选段后面。
- 没有重排时，全部记录按 RRF 分数 × 淡化系数排序。
- 以上分数相同时再按可信程度（`owner_confirmed` > `owner_stated` > `observed`）排序，仍相同时按更新时间从新到旧排序。
- A3.3 中没有淡化，淡化系数视为 1。

第 1 轮验收技术澄清：向量缓存身份由插件 ID、版本、扩展声明（含维度）和生效配置指纹派生。身份变化后不使用旧向量，后台重新生成。重排只改变候选段的顺序，其余记录仍按融合顺序接在后面。语义路仅接收余弦相似度严格大于 `memory.semantic_min_similarity` 的候选，默认 0.5；真实模型选型时校准。

### 4.2 降级

- 没有配置向量模型、或它出错、超时：只用关键词，不报错。`status` 显示提醒，日志 WARN 每小时最多一次。
- 重排扩展不可用：跳过重排。
- 检索整体出错：本次上下文不注入检索结果（核心记忆照常注入），回复照常进行。

### 4.3 向量的维护

- 写入或修订记录后，在后台为新修订生成向量；生成前这条记录只能被关键词找到。
- 更换向量模型（`embedder_id` 变化）时，后台逐条重建；重建期间旧模型的向量不参与计算。`status` 显示重建进度。
- 重建和生成向量不调用生成模型，不消耗对话额度。

### 4.4 新增扩展点 `memory.reranker`

`async rerank(query: str, records: list[MemoryRecord], cancel) -> list[float]`，返回和 `records` 等长的分数。只接收投影内的记录。按 SDK 版本策略作为兼容扩展，写入 CHANGELOG，并加入 plugins.md 的扩展点表。

### 4.5 真实模型的选型（不在 A3.3 实现）

- A3.3 只实现流程和假向量模型、假重排模型的测试。
- 真实的向量模型和重排模型插件，在切换上线前选型（用户已确认：效果优先，不为节省空间降低精度）。候选包括 Qwen3-Embedding 系列、bge-m3，以及选型时出现的更好的模型，配合对应的重排模型；按部署机器（含将来的云服务器）的显卡和内存决定规格。
- 下载前告诉用户名称和大小，得到同意才下载。
- 对比用一套虚构的测试题（口语化、零碎的中文记忆，例如"上次那家很咸的拉面"要能找到"那家拉面太咸了"），谁找得准用谁。用不用真实记忆做对比要另外征得用户同意。

### 4.6 记忆容量的实测调整（用户已确认）

第 5.1 节的预算是默认值，最合适的容量和检索准确度绑在一起，在选型时一起实测：

1. **想起率**（不调用对话模型，本机运行）：虚构测试记忆（例如 500 条）和问题（例如 100 个），分别试 `recall_limit` = 5、10、15、20，统计相关记忆被带上的比例。
2. **干扰**（调用线上模型）：用几组不同的容量看回复里是否扯进无关的记忆。需要用户本次明确同意，先给用户看测试句子。

取"再多带也不提高想起率、反而开始增加干扰"的那一点，写入部署配置。

## 5. 想起与上下文

### 5.1 注入（agent-spec §4.1 第 4 项）

每次调用模型时，在"最近任务"之后注入"记忆"段：

1. **核心记忆**：投影内 `basis = owner_confirmed` 的记录，以及 `kind = preference` 且 `basis = owner_stated` 的记录（不含 `kind = profile`、`kind = jargon`，见 memory-recall-spec §4.1，用户已确认，Issue #39 U3），按更新时间倒序，总量不超过 `memory.core_chars`（默认 4000 字，用户已确认）。装不下的记录不丢，照常参与检索；`status` 提示"有 N 条核心记忆没有每次带上"。
2. **想起的记忆**：用本批次消息加上最近 3 条聊天记录作为查询，按第 4 节检索；去掉已在核心记忆中的记录，最多 `memory.recall_limit` 条（默认 10），总量不超过 `memory.recall_chars`（默认 3000 字，用户已确认）。

预算按 Unicode 字符计算，只裁掉整条，不截断一条记忆。默认值在选型时按第 4.6 节实测调整。

**从零开始**（用户已确认）：
- 当前场景投影内一条有效记忆都没有时，记忆段仍然注入，只写一句固定文字"你们之间还没有记住的事"。投影内有记忆、只是这次没检索到相关的，不写这句，只注入核心记忆。
- 新伴侣从空库开始，靠聊天认识主人；**不提供预置记忆或初始资料**。称呼等设定写在配置和人设中，不属于记忆。以后由 WebUI 提供"主人亲自添加"的管理操作时再单独设计。

- 每条格式：`[记忆N] 内容（大约时间）`。大约时间用"今天""上周""三个月前"这类说法，由本体按 `created_at` 生成。`N` 在本次回复的工具循环内有效：同一记录沿用编号，新记录接续编号；再次注入时更新对应修订号，本体在内部映射到记录 ID 和修订号；不暴露真实 ID。
- 主动消息（agent-spec §15）按目标会话的场景做同样的注入。

### 5.2 说话方式（本体规则，仓库中的固定文字）

- 自然地用记忆，不说"根据记录""我的记忆显示"，不报日期和编号。
- 很久以前的小事可以记得模糊一些。
- 不确定时可以问；真不记得就直说，不编。
- 人设描述的是她是谁、怎么说话、和主人是什么关系；**具体发生过的共同经历只以记忆和任务记录为准**，人设里的关系设定不等于具体发生过的事。
- 记忆和聊天记录冲突时，以主人最近亲口说的为准，并用 `core_remember` 的 `replaces` 修订旧记忆。

### 5.3 `core_recall`（主动回想）

- 参数：`query`（她想回想的内容）。
- 结果：投影内的记忆检索结果（前 10 条，格式同第 5.1 节，编号接续），加上本会话按 kernel-spec §13.1 可见的 task 记录中与查询相关的条目（不限 24 小时，最多 10 条，格式同 agent-spec §4.3）。
- 两处都没有找到时，结果明确写"记忆和任务记录里都没有找到相关的事"。
- 每条记录（一次回复）最多调用 3 次。不计入 `memory.max_writes_per_record`。

## 6. L6：不认下没发生的事

- 本体规则（agent-spec §4.3 的规则扩展到记忆）："对方说起一件你们之间的事、或说你答应过什么时，先看任务记录和记忆；都没有时用 `core_recall` 回想；仍然没有，就直说不记得，不顺着认下。"
- 离线回归（假模型）证明的是**本体给出了正确的证据**：
  1. 虚构前提（"你上次答应给我画猫"），账本和记忆都没有：`core_recall` 的结果为"都没有找到"。
  2. 有记忆的情况：同样的问题能检索到对应的 `[记忆N]`。
  3. 记忆在私聊、问题在群里：群里的 `core_recall` 找不到私密记忆，结果同样是"都没有找到"。
  4. 记忆被撤销后：再也找不到。
- 真实模型是否遵守（不认下、不编），在切换上线前用真实模型抽检，需要用户本次明确同意，并先给用户看句子清单。

## 7. 出站检查：私密记忆泄露（agent-spec §9.2 的预留行）

- 适用：对外场景，以及不在 `memory.private_scenes` 中的对内场景。
- 读取方式：本体专用的守卫读取。它比较的是全部有效的 `private` 记录，但只返回"是否命中"，不返回原文；不经过插件视图、检索器和重排扩展，结果不进入上下文。命中的记录内容不写入日志、审计和改写提示。
- 方法：把要发出的文字和**全部**有效的 `private` 记录内容都做 agent-spec §9.2 的规范化（NFKC、小写、去掉空白和零宽字符），再去掉标点；发出文字中出现任意一段长度不少于 `memory.leak_min_chars`（默认 8）、与某条私密记录内容完全相同的连续片段，就算命中。
- 命中后按隐私类处理：改写一次，仍命中就拦下（agent-spec §9.3）。给模型的改写提示只说"包含了不能在这里说的私密内容"，不附私密记录原文。
- 这只能拦住原句照搬，拦不住换种说法的泄露。后者靠投影保证：对外场景本来就拿不到私密记忆。

## 8. 导出（data-and-backup §2）

- 命令：`python -m clytie memory export <cid> --out <路径>`。可以在伴侣运行时执行，用 SQLite 备份接口取一致快照。
- 空库（还没有 `companion_uid`）不能导出，提示"还没有记忆，不需要导出"，不生成文件。
- 包内容：记录、全部修订、审计中与记忆有关的条目、记录引用的资产（A3.3 中没有引用资产的记录类型，框架预留）。**不含**向量、账本、聊天原文、凭据、其他伴侣的数据。
- 加密：每个包使用随机生成的内容密钥，AES-GCM 认证加密；内容密钥再分别用两种方式包裹，**任一种都能打开**（用户已确认）：
  1. **口令**：用户口令经 KDF（由 cryptography 提供，例如 Scrypt；参数写在包头）派生密钥。口令不保存，交互输入，至少 12 个字符；测试通过 API 直接传入。
  2. **恢复码**：第一次导出时生成，**只显示这一次**，提示用户打印或存入密码管理器。实例中只保存"用恢复码加密"所需的部分（例如 RFC 7748 定义的椭圆曲线公钥，存在 `secrets/` 中），**不保存能用恢复码路径解密的任何东西**。以后的每个导出包都同时加上恢复码这一层。
  - 包不使用实例备份密钥，这样能导入到别的实例。
  - `memory recovery-code new`：重新生成恢复码（需要确认）；旧包仍然只能用旧恢复码或各自的口令打开，提示用户保留旧恢复码。
  - 忘记口令、但实例还在时，直接重新导出并设新口令即可，不需要旧口令。
- 导出后自动校验：用口令解密、比对每个文件的 SHA-256、打开数据库、核对记录数；恢复码层只能做格式检查（实例没有恢复码）。校验通过才算成功，写审计。
- 具体算法与包格式写入 ADR，使用成熟库提供的实现，不自行实现加密算法。
- `--format jsonl`：不加密的文本快照，按记录 ID 排序，每条一行，包含修订号，只写到 `CLYTIE_HOME/exports/`。只用于对比，不能用于导入。

## 9. 导入（data-and-backup §3）

### 9.1 流程

**导入只有一种含义：把她自己的记忆搬回她自己**（用户已确认）。换电脑、上云、重装、从旧系统迁移都属于这一种。不支持把另一个伴侣或别人的记忆导入进来，见第 12 节。

所有导入都**分两步**，方式与插件连带停用相同：

1. **计划**（只读）：`memory import plan <cid> <包> --mode new|restore|merge`。解密并校验包，然后预览：新增、更新、冲突、跳过、（恢复模式下）当前库中比包里更新、将被撤销的记录。返回计划标识。
2. **确认后执行**：`memory import apply <计划标识>`。计划生成后，记忆库或包发生任何变化，计划失效，必须重新生成。

预览的显示（用户已确认）：
- 默认只显示数量、记录编号、动作和可见等级，**不显示记忆原文**。这些命令有时由 AI 协作者代为运行，原文会进入对方的对话上下文。
- 加 `--show-content` 才显示原文（冲突时显示两边的内容）。
- 计划文件只保存记录编号、动作、指纹和冲突选择，不保存记忆原文、口令或恢复码。`apply` 时重新交互输入口令解密，持锁核对指纹后再快照、写入。
- 冲突选择的格式、计划文件的位置写入 ADR。

执行顺序：
1. 确认伴侣**已停止**（取得记忆库的锁；A3.3 所有导入模式都要求停止，在线导入留给 A4 的管理接口）。
2. 自动快照：当前记忆库用实例备份密钥加密，保存到 `backups/memory/<cid>/pre-import-<UTC时间>.enc`，立即解密校验，失败就不导入。
3. 在一个事务中写入，同时写修订和审计。
4. 返回导入编号。

### 9.2 三种模式

| 模式 | 规则 |
|---|---|
| `new` | 目标伴侣的记忆库必须是空库（第 1.1a 节），否则拒绝 |
| `restore` | 必须是她的记忆（见下）。计划中列出"当前库中比包里更新的记录"，确认后把库改成与包一致。**用修订完成，不替换文件**（用户已确认）：包里有的写成包里的版本，包里没有的标为撤销，全部留在修订历史里 |
| `merge` | 必须是她的记忆（见下）。按记录 ID 和修订号：缺少的补上；只有一边在共同修订之后改过的，改过的一方生效；两边都改过的列为冲突 |

**是不是她的记忆**（用户已确认：按身份标识判断，不按导入模式，也不按配置里的编号）：

| 情况 | 判断 |
|---|---|
| 目标已有 `companion_uid` | 与包里的相同才允许 `restore` / `merge`；不同就**拒绝**，提示"这不是她的记忆"，不做任何改动 |
| 目标是空库（例如新电脑上刚建好） | 只能 `new`。计划显示包里伴侣的编号、记忆条数、导出时间，用户确认"这是她的记忆"后才能执行；新库沿用包里的 `companion_uid` |
| 其他格式（导入器，第 9.4 节） | 见第 9.4 节 |

- 每次导入产生的修订都带导入编号，用于撤销导入（第 9.3 节）。
- **共同祖先**按修订的内容指纹链判断，不只比修订号：两边最后一个相同指纹的修订是共同祖先。
  - `new` 模式和没有分叉的 `merge`：把包里的修订原样保留。
  - 分叉后选择"使用包里的"，或 `restore`：在本地历史后面追加一个新修订，内容等于包里的版本；包里分叉出去的那段历史另外保存（标明来自哪个包），不覆盖本地历史。
  - 包里的审计条目标明来源，不冒充本地执行。
- **来源会话和主人**：会话逻辑 ID 和主人的 `actor_id` 随实例配置一起迁移，保留原值，`basis` 原样保留。包里的某个会话在当前配置中不存在时，该会话来源的记录只在对内场景可见，`status` 提示有多少条记录的来源会话找不到；以后由 WebUI 提供手动对应。A3.4 起保留原编号并按会话清单处理，见 memory-recall-spec §4.6（用户已确认，Issue #39 U4）；A3.3 格式的旧包仍设为 `null`。
- 冲突逐条选择"保留当前"或"使用包里的"，没有默认值；有冲突未选择时，计划不能确认。
- 幂等：同一个包再次 `merge`，包里的修订本地都已经有了，全部记录为"跳过"，不产生新修订；本地之后的修改保留。再次 `restore` 则按新计划重新对齐到包的内容，计划中列出会被改回的记录。
- 空库保护：包里没有任何有效记录、而目标库有记录时，`restore` 和 `merge` 一律拒绝。导入器和初始化数据也一样，**不能用空库或种子数据覆盖已有记忆**。

### 9.3 撤销导入（用户已确认：只撤这次导入带来的改动）

目的：避免很久以后误撤一次导入，把之后记下的东西一起丢掉。

- `memory import undo <导入编号>`：同样先生成计划、再确认，伴侣必须停止。
- **只撤回这次导入的修订**，导入之后她新记的、改的记忆一条都不动：
  - 这次导入新增的记录：标为撤销。
  - 这次导入修改或撤销的记录：改回导入前的版本。
  - 导入之后又被改过的同一条记录：列为冲突，逐条选择"保留现在的"或"改回导入前"，没有默认值，不选不能确认。
- 全部用新的修订完成，不删除任何东西；撤销导入本身也会得到一个导入编号，可以再撤销。
- 计划写明"这是 N 天前的导入，将撤回 X 条、改回 Y 条、冲突 Z 条"。
- 改回导入前的版本时，`basis` 也按导入前的值恢复（第 1.3 节的例外），会降低可信程度的记录在计划中单独列出。
- 执行前同样先做快照（第 9.1 节第 2 步）。

### 9.4 导入器扩展（她过去在其他系统里的记忆）

导入器把其他格式（例如旧系统）里**她自己**的记忆转成标准记录，同样算搬家。

- **只能导入到空库**（`new`），之后同样有计划、快照、撤销。合并到已有记忆的库不在 A3.3 范围。
  - 唯一的例外：目标库的 `companion_uid` 正是由**同一个导入器、同一份源数据**的导入产生的，并且库里除了导入和撤销导入以外没有任何其他修订（她和插件都还没写过）。这时可以再次导入，用于撤销导入后重做，或切换前的试导入。源数据用指纹判断，计划中写明。
  - 再次导入时可信程度**以本次的选择为准**（用户已确认，Issue #30）：本次不同意提议时，之前采用了提议的记录降为 `observed`。计划中单独列出"会被降低的 N 条"，整体确认一次，不逐条选择。
- 导入器只读打开源数据的副本。
- **账号和会话**：导入器给出源数据里的平台账号和平台会话（例如旧系统里的账号号码、群号），由本体通过当前实例配置里的账号映射，对应到 `actor_id` 和会话逻辑 ID；导入器不能直接填 `subject` 或 `origin_conversation_id`。对应不上的，`subject`、`origin_conversation_id` 为 `null`，只在对内场景可见，不进入核心记忆。不凭名字或昵称对应。
- **可信程度**（用户已确认）：
  - 导入器可以**提议**每条记录的可信程度（例如旧系统中标为"已确认"的记录提议为 `owner_confirmed`）。
  - 计划中按提议列出数量。用户明确同意后才采用提议，不同意时全部为 `observed`。
  - 只有 `subject` 对应到主人的记录才能采用 `owner_confirmed` / `owner_stated`，其余一律 `observed`。导入器自己的提议不算确认。
- 本系统自己的导出包由本体识别（格式、解密认证、清单校验），是第 1.1 节"忽略外部可信字段"的唯一例外：包里的 `basis` 和 `origin_conversation_id` 按第 9.2 节保留或规范化。导入器不能声称自己产生的是本系统的导出包。
- A3.3 只用测试中定义的虚构导入器验证流程。旧系统的导入器和真实记忆的迁移在切换上线时单独进行，需要用户另外同意；真实数据和其中的任何内容都不进入仓库。

### 9.5 快照保留

`backups/memory/<cid>/` 中导入前快照保留最近 5 份；更早的在下一次导入成功后逐个文件删除并记录。常规的记忆备份（重要写入后、每天一次）属于 A4 的守护进程，不在本文件范围。

## 10. 配置（`memory` 段新增，全部可选）

| 字段 | 类型（默认值） |
|---|---|
| `core_chars` | 整数 200–50_000（4000） |
| `recall_chars` | 整数 200–50_000（3000） |
| `recall_limit` | 整数 1–50（10） |
| `semantic_min_similarity` | 数值 -1–1（0.5）；语义路仅接受余弦相似度严格大于此值的候选；离线技术默认值，真实模型选型时校准 |

`embedder`、`reranker` 指向的插件必须已启用并实现对应扩展点，否则配置无效。

## 11. 离线验收

全部使用临时实例目录、MockClock、假平台、假模型、假向量模型和虚构数据。

1. **当场记**：主人私聊说一件事，假模型调用 `core_remember`；记录的 `subject`、`source_ref`、`source_type`、`basis = owner_stated` 由本体填写；`explicit = true` 时为 `owner_confirmed`，`write_mode = confirmed`。
2. **工具提供条件**：群友说话时，模型请求里没有 `core_remember` 和 `core_forget`，但有 `core_recall`；主动消息生成时三个都没有，记忆照常注入。
3. **修订与撤销**：用 `replaces` 修订后修订号加 1，旧版本在修订表里；`core_forget` 后任何场景都检索不到；`expected_revision` 不一致时返回冲突；超过写入次数上限时拒绝。
4. **去重**：
   - 相同内容写两次只有一条记录。
   - 插件在群聊场景写入与一条私密记录相同的内容：新建一条，返回值中没有私密记录的 ID、来源或时间。
   - 主人明确再说一次时升级为 `owner_confirmed`；聊天和插件的写入都不会降低可信程度；插件修订或撤销 `owner_confirmed` 或 `owner_stated` 的记录时返回"找不到"，修订 `observed` 的记录可以成功。
5. **投影（原 A3 第 5 项）**：群聊场景中，上下文、`core_recall`、插件记忆视图、检索器的 `CandidateReader` 都拿不到私密记忆；`get` 对私密记录返回 `None`；陌生人私聊不注入记忆。
6. **来源群限制**：在群 A 由主人说的 `public` 记录，在群 A、主人私聊和家庭群（对内场景）能检索到，在群 B 检索不到；插件传入的 `source_type`、`scope` 不改变结果；没有绑定会话的插件写入只在对内场景可见。
7. **检索**：关键词检索能找到两字中文词；假向量模型下语义检索能找到关键词找不到的记录；融合结果可复现；`owner_confirmed` 同等相关时排在前面；向量模型抛错时退回关键词并有提醒；更换 `embedder_id` 后旧向量不参与计算、重建后恢复。
8. **上下文注入**：核心记忆和想起的记忆按预算整条裁剪，格式为 `[记忆N] 内容（大约时间）`，不出现真实记录 ID；核心记忆装不下时 `status` 有提示；主动消息按目标场景注入。
9. **私密记忆泄露**：群聊回复中照搬私密记忆里 8 个字以上的片段时，改写一次；仍命中时拦下，执行状态为 `error`、`error.code = outbound_blocked`；改写提示、日志、审计里都不含私密原文；插件视图和检索器在群聊场景中拿不到被比较的私密记录。
10. **L6**：第 6 节的 4 个场景。
11. **导出**：加密包能通过校验；用口令和用恢复码都能打开同一个包；用错口令或恢复码明确报错、不产生残缺输出；实例目录中找不到能用恢复码路径解密的材料；重新生成恢复码后旧包仍能用旧恢复码打开；包里没有向量、账本和聊天原文；jsonl 文本快照按 ID 排序，可重复生成且内容相同。
12. **导入（原 A3 第 7 项）**：
    - 三种模式按第 9.2 节运行；
    - 计划生成后库或包变化时计划失效；
    - 冲突不选择时不能确认；
    - 导入前自动快照并校验；
    - 重复导入全部跳过；
    - 空包不能覆盖有记录的库；
    - 伴侣运行时拒绝导入；
    - 预览默认不含记忆原文，`--show-content` 才显示；计划文件中没有原文、口令和恢复码；
    - 分叉合并保留本地历史，包里分叉的历史另存；
    - 身份标识：库建立后、写入第一条记录前没有标识；已有标识相同才允许 `restore` / `merge`，不同时拒绝且不做任何改动（配置编号相同也一样）；空库只能 `new`，用户确认"这是她的记忆"后新库的标识与包相同；写过又撤销的库不再是空库；
    - 导入器：只能导入空库；同一导入器、同一源数据产生的、未被写过的库可以再次导入，其他情况拒绝；账号由本体经配置映射，对应不上的记录 `subject`、`origin_conversation_id` 为 `null`，只在对内场景可见；可信程度的提议需要用户在计划中同意，不同意时全部为 `observed`，对应不到主人的记录不能采用主人的可信程度；再次导入时按本次选择写入，本次不同意时之前采用提议的记录降为 `observed` 并在计划中单列；
    - 同一伴侣但会话在当前配置中不存在：该会话来源的记录只在对内场景可见，`status` 有提示；
    - `restore`、撤销导入、冲突选择可以按目标版本降低 `basis`，计划中单独列出；聊天和插件的操作不会降低；导入不写入任何记忆，只写审计；
    - 恢复模式通过修订完成，包里没有的记录变为撤销、修订历史完整；
    - 撤销导入只撤回该次导入的修订：导入之后新写的记录保持不变，导入之后又改过的记录列为冲突；撤销导入本身可以再撤销。
13. **导入器扩展**：一个只在测试中定义的虚构导入器，不修改本体就能接入；它直接填写 `subject`、`origin_conversation_id` 或声称自己是本系统导出包时都不生效。
14. **从零开始**：空库启动时记忆段只有"你们之间还没有记住的事"；第一次 `core_remember` 后生成 `companion_uid`，之后不变；空库导出被拒绝且不生成文件；有记忆但没检索到相关的时不出现这句。
15. **写入失败不影响回复**：记忆库写入抛错时，回复照常发出，记 WARN。

## A4.2 管理入口的执行与中断

记忆业务规则保持本文件规定；API 运行中转交伴侣子进程，停止时转交独立管理工作进程，两者共用 MemoryAPI。restore 和撤销导入仍要求伴侣停止。稳定操作标识、串行与启动互斥、取消检查点、数据库和文件的提交核验、强杀后的恢复与阻止规则统一见 api-spec §4.3a（Issue #57，用户已确认）。HTTP 请求结束不决定事务结果，不自动重做管理操作；恢复码生成成功与结果送达分别记录，原文仍不持久化。
