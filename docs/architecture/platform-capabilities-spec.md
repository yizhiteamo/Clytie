# 平台能力的插件化路线

状态：草案（2026-11-18），待用户确认。

本体只做所有伴侣、所有平台都需要的事。和某个平台有关的功能，一律放在平台插件或能力插件里。本文规定两者的分界、平台数据怎么提供给能力插件、能力包，以及现有越界代码的清理。

## 1. 分界规则

| 放在哪里 | 内容 |
|---|---|
| 本体 `src/clytie/` | 账本、记忆核心、准入、边界与出站检查、守护进程、备份、本机 API、插件宿主、SDK，以及与平台无关的测试工具部分 |
| 平台插件 | 连接平台、事件翻译、发送、平台专属的采集和测试驱动、平台专属服务 |
| 能力插件 | 给模型调用的工具；需要平台数据时，通过服务接口取得 |

- **本体代码不出现具体插件的 id 和平台名**（`sdk/testing/` 中的假插件除外）。CI 中由 `scripts/check_architecture.py` 检查：读取 `plugins/*/plugin.json` 的 id，在 `src/clytie/`（不含 `sdk/testing/`）的代码中出现即失败。
- 本体需要某种平台能力时，按"支持这项能力的插件"调用，例如 `ChannelFeatures` 中的 `supports_membership`，不按插件名判断。
- 插件只 import `clytie.sdk`（AGENTS.md 3.4，现有检查不变）。

## 2. 平台数据：通用服务与平台专属服务

**优先做成通用服务。** 多个平台都有的概念（会话历史、会话中的媒体、成员信息），定义成与平台无关的**会话服务**：

- 平台插件在清单中声明自己实现的会话服务，例如 `{"name": "history", "version": "1.0", "methods": ["recent"]}`。
- 能力插件声明需要的会话服务，调用时传入会话逻辑 ID：`ctx.conversation_services(conversation_id).get("history")`。宿主找到该会话所属平台插件的实现并转调；该平台没有实现时返回 `None`，能力插件如实告诉模型"这里拿不到"。
- 会话服务的参数和结果用 SDK 定义的通用类型，不含平台原始字段。返回内容经过本体的隐私投影，规则与上下文相同（agent-spec §9）。
- 每一种会话服务第一次出现时，先在 sdk-spec 中定义它的方法和类型，再实现。

**确实只属于某个平台的功能**（例如某平台独有的群文件、签到），做成平台专属服务：

- 由平台插件提供，服务名以平台为前缀（如 `qq.group_files`）。
- 依赖它的能力插件在清单中声明，并在 `catalog.json` 中标出适用平台。伴侣没有绑定该平台时，宿主不启用这个能力插件，并说明原因。
- 能做成通用服务的，不做成平台专属服务。是否通用，在该服务的规格中说明理由。

本节的 SDK 新增（会话服务）在第一个需要平台数据的能力插件（如群历史）开始时实现，本期只定规则。

## 3. 能力包

接入一个平台常常带来一组相关能力。**能力包**是一份只有清单、没有代码的插件包：

- 清单列出包含的插件、各自的默认配置，以及适用平台。
- 对某个伴侣启用能力包，等于生成一份"连带启用"计划（plugins.md §6 的依赖解析与确认流程），确认后一并启用。停用同理，按已有的连带停用计划执行。
- 能力包不能改变准入、边界和工具使用范围（`tool_scopes`）；包里插件的权限照常逐项列出、逐项确认。
- 启用后，包内插件仍可单独停用和配置。能力包只是批量操作的入口，不是新的运行单位。

能力包在官方插件数量足够需要分组时实现（预计与创意工坊同期），本期只定规则。

## 4. 本期清理：现有越界代码

| 现有位置 | 问题 | 改法 |
|---|---|---|
| `src/clytie/api/emoji.py`、CLI `clytie emoji capture` | 写死 `qq-onebot` 的路由 | 移到 qq-onebot 插件的 `cli_command` 扩展（已有扩展点），通过 `ApiClient` 调用插件自己的路由 |
| `src/clytie/api/config_write.py`、`management.py` 中的 `/companions/<cid>/emoji/apply` | 本体认插件名和 `emoji_ids` 配置键 | 改为通用的"插件配置提议"：见 4.1 |
| `src/clytie/smoke/` 的 OneBot 驱动与目标解析 | 本体直接说 OneBot 协议、按 `qq-onebot` 找账号 | 驱动移到平台插件，本体只留用例、判定、摘要路由和报告：见 4.2 |

### 4.1 插件配置提议

插件不能自己改伴侣配置。需要写回配置时（例如采集到的表情编号），由插件**提议**，本体确认后写入：

- 插件路由返回一份提议：要改的键、新值，范围只限**该插件自己的绑定配置**（`channels[].config` 或 `plugins.<id>.config`）。
- 本体通用路由 `POST /companions/<cid>/plugins/<pid>/config/apply`（需要确认）取回提议，按该插件的配置 Schema 校验，写入配置并保留历史，规则与现有配置写入相同。
- 本体不认识具体的键；键是否允许写回，由插件清单声明（`config_writable: ["emoji_ids"]`）。未声明的键一律拒绝。
- 原路由 `/companions/<cid>/emoji/apply` 保留一个次版本作为兼容入口，转到新路由，然后删除。

### 4.2 冒烟测试驱动

- SDK 新增扩展点 `smoke_driver`：平台插件提供测试方驱动，只在 `clytie smoke run` 的命令行进程中加载，不在伴侣进程中运行。
- 驱动接口：`connect(config, secrets)`、`authorize(target) -> (人数, 第几个账号)`、`send(case) -> 测试方消息编号`、`events()` 产出通用观察（回复：字数、有无图片、到达时间；状态表情：状态名、添加或撤销、到达时间）、`close()`。表情编号到状态名的换算由驱动按自己的绑定配置完成。
- 本体负责：读用例和上限、当次确认、伴侣状态检查、按会话配置和人物登记算出目标（会话的平台 ID、伴侣账号、测试人物在该平台的账号，用会话配置中的 `channel` 字段，不写死平台名）、判定、摘要路由、报告。smoke-spec §4–§9 的规则不变。
- `smoke.yaml` 中协议端地址和令牌文件改为驱动自己的配置段：`driver: {plugin: <id>, config: {...}}`。现有私有配置由实现会话迁移。

## 5. 官方插件仓库

- **暂不拆仓**（沿用 2026-11-15 的决定）：SDK 到 1.0、不再频繁变化，或开始接受第三方插件时再拆。SDK 仍在快速变化，现在拆仓，每次改 SDK 都要两个仓库协调版本。
- 为了以后拆仓只是"搬目录"，现在就保证：每个官方插件自带清单、代码、测试和 README，只依赖 `clytie.sdk` 和清单中声明的版本范围；本体不引用任何插件（第 1 节的检查）；插件测试不 import 本体内部模块。
- 拆仓时另写方案（版本发布、CI、兼容矩阵），交用户确认。

## 6. 验收（本期清理）

1. `check_architecture.py` 新增"本体不出现插件 id"检查，有反例测试；清理后 `src/clytie/`（不含 `sdk/testing/`）中没有 `qq-onebot` 等插件 id。
2. 表情编号采集：通过 qq-onebot 的 `cli_command` 完成采集，经通用配置提议路由写入；未声明的键、其他插件的配置、非该插件的绑定都被拒绝；需要确认；兼容入口转发正确。
3. 冒烟测试：驱动移到 qq-onebot 后，现有 B5 离线测试全部通过（必要时只改夹具的装配方式）；本体部分在没有任何平台插件时也能用假驱动跑通。
4. SDK 次版本号增加，sdk-spec 补充 `smoke_driver`、`config_writable` 和插件配置提议；会话服务和能力包只写规则，不实现。
5. 双平台 CI 通过；真实平台连接和模型调用为 0。清理后由用户当次同意，跑一次冒烟测试确认行为不变。

规模预估：1–1.5 天。
