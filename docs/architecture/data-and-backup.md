# 数据、导入导出与备份

## 1. 实例目录 `CLYTIE_HOME`

所有运行时数据和部署专属文档都在实例目录中，与公开的代码仓库分开。位置由环境变量 `CLYTIE_HOME` 指定，未指定时默认为仓库同级的 `Clytie-home/`。`examples/home/` 提供一份虚构的示例。

```
Clytie-home/
├─ AGENTS.local.md            部署专属规则（开发时必读，见仓库 AGENTS.md 第 0 节）
├─ docs/                      部署专属文档（伴侣设定说明、旧系统迁移记录、私有问题记录）
├─ private-denylist.txt       本机提交扫描用的真实名字/号码名单
├─ clytie.local.yaml          全局配置：平台账号映射、会话逻辑名、通知方式
├─ secrets/                   凭据和登录态（WebUI 不显示内容）
├─ companions/<companion-id>/
│  ├─ companion.yaml          模型、平台账号、启用的插件及配置、场景与人设层
│  ├─ persona/                人设文件
│  ├─ memory/                 记忆库及记忆资产
│  ├─ ledger/                 统一任务账本
│  ├─ plugin-data/<plugin-id>/
│  └─ logs/
├─ shared/assets/             内容哈希资产库
├─ plugins/                   从创意工坊安装的插件
├─ backups/                   加密备份及回执
├─ exports/                   导出的记忆包和文本快照
└─ run/                       进程锁、健康状态
```

迁移到另一台电脑 = 克隆代码仓库 + 恢复实例目录的备份。

## 2. 记忆导出

**默认内容**：该伴侣的记忆库（含修订记录、可见等级、来源信息）、档案、黑话、经历、记忆引用的资产。
**不导出**：凭据、登录态、账本、聊天原文、其他伴侣的数据。

**加密包** `.clytie-memory`：

```
manifest.json      格式版本、伴侣 id、导出时间、Clytie 版本、记录数、各文件 SHA-256
memory.db          SQLite 备份接口生成的一致快照
assets/            记忆引用的资产
```

- 用用户设置的口令加密，口令不保存在包内。
- 导出后自动校验（解密、比对哈希、打开计数），通过才算成功；写审计记录。

**文本快照**（可选）：`memory export --format jsonl` 生成按记录 ID 排序、格式固定的文本（每条记录一行，含修订号），不加密，只写到 `CLYTIE_HOME/exports/`。用于用户自己做版本对比（见第 5 节），不用于恢复。

## 3. 记忆导入

| 模式 | 规则 |
|---|---|
| 新建伴侣 | 目标必须是空的 |
| 恢复 | 该伴侣必须先停止；自动快照；列出"当前库中比包里更新的记录"，确认后执行 |
| 合并 | 按记录 ID 和修订号：缺少的补上，修订号更新的一方生效，两边都改过的列为冲突逐条选择 |

- 先校验、再预览（新增、更新、冲突、跳过），确认后写入。
- 幂等：同一个包重复导入不产生重复记录。
- 绝不用空库或种子覆盖已有记忆；任何导入前先快照，可以撤销。
- **导入器是插件**（扩展点 `memory.importer`）：其他格式、其他系统的数据由导入器转换为标准记录后，走同样的合并流程。导入器只读打开源数据的副本。

导入导出先以 CLI 实现，WebUI 再包装。

## 4. 备份

代码由 git 管理。实例目录单独做加密备份：

| 内容 | 频率 |
|---|---|
| 记忆库 | 重要写入后（合并窗口内一次）+ 每天一次 |
| 账本、插件状态、配置、人设、部署文档 | 每天一次 |
| 凭据 | 不进入常规备份，由用户自行保管 |

- 每个快照都是完整的，最新一份包含全部记忆和修订记录。
- **保留策略**（可配置）：最近 30 天每天一份；一年内每周一份；更早每月一份；最近 3 份始终保留；永不删光。清理时一次删除一个明确文件并记录。
- **恢复校验**：备份后在临时目录解密、打开、计数，完成后只删除本次创建的那个临时目录；结果写入 `backups/latest.json`。
- 由守护进程在运行时执行，不创建系统定时任务；不自动上传远端。

### 4.1 备份密钥

- 常规备份和插件升级快照共用一把**实例备份密钥**，保存在 `CLYTIE_HOME/secrets/backup.key`。首次需要时自动生成（加密安全的随机数），之后不自动更换。
- 密钥文件不进入任何备份（凭据不进入常规备份）。因此首次生成密钥时必须提示用户：把密钥另外保存一份（例如打印或存进密码管理器），**丢失密钥就无法恢复任何备份**。提供 `python -m clytie backup show-key-fingerprint`（只显示指纹，用于核对）和 `python -m clytie backup export-key <路径>`（导出到用户指定位置，需要确认）。
- 加密使用成熟库提供的认证加密（AEAD），不自行实现加密算法；具体库和算法由实现者选择并写 ADR。
- 每个加密文件带格式版本和密钥指纹；用错密钥时明确报错，不产生残缺输出。
- 记忆导出包使用用户口令（见第 2 节），**不使用**备份密钥，以便导入到其他实例。

### 4.2 插件升级快照

升级的触发和确认见 `plugins.md` 第 6.1 节。这里只规定快照和恢复。

- 插件升级执行 `migrations/` 之前，宿主把该插件在该伴侣下的私有状态目录 `plugin-data/<plugin-id>/` 整体打包、用备份密钥加密，保存为：
  `CLYTIE_HOME/backups/plugin-upgrades/<companion-id>/<plugin-id>/<旧版本>-to-<新版本>-<UTC时间>.enc`
  （文件名中的版本是 `data.version`。）
- 快照写入后立即校验（解密、比对哈希），校验失败就**不执行升级**。
- 迁移失败时自动恢复。恢复**不逐个删除**迁移产生的文件，而是整体换目录：
  1. 把快照解密到实例目录内的临时目录，并校验。
  2. 把出错的私有状态目录整体改名，移到 `backups/plugin-upgrades/<companion-id>/<plugin-id>/failed-<旧版本>-to-<新版本>-<UTC时间>/`。
  3. 把临时目录改名为 `plugin-data/<plugin-id>/`。

  任何一步失败就停止，不再做别的改动，并报告各目录当前的位置。
- 故障目录保留供排查，宿主**不在未确认时删除**。
- **提醒**：只要还有故障目录，`status` 输出（以后 WebUI 也是）就持续显示一条提醒，列出每个故障目录的位置、大小和总占用。该插件之后迁移成功时，提醒中注明"问题已解决，可以清理"。
- **清理**分两步，方式与连带停用相同：
  1. 计划（只读）：列出将要清理的故障目录、各自的文件数和大小。
  2. 确认后执行：带计划标识确认。计划生成后目录内容变化时，计划失效。
  - 宿主只清理计划中列出的 `failed-…` 目录：逐个删除其中的文件并写记录，最后删除空目录。不使用递归删除命令；遇到符号链接、越出该目录的路径或计划外的文件时停止并报告。
  - 只在用户确认时执行，没有定时自动清理。
- 每个伴侣的每个插件保留最近 3 份升级快照（只算 `.enc` 文件，不含故障目录）；清理时一次删除一个明确文件并记录。
- 宿主只恢复私有状态，不改动插件代码（见 `plugins.md` 第 6.1 节）。
- 插件私有状态以外的数据（记忆、账本）不在升级快照范围内；记忆由常规备份负责。
- 测试只使用临时实例目录和测试生成的密钥，不读取真实实例目录中的密钥。

### 4.3 迁移日志与"恢复未完成"

目的：迁移或恢复中途出错、甚至进程崩溃时，重启后不会让任何代码加载半迁移的数据或一个空目录。

**迁移日志**
- 每个伴侣的每个插件一份：`companions/<companion-id>/plugin-recovery/<plugin-id>.json`，只有宿主能读写，原子写入。
- 内容：计划标识、迁移前的版本记录（`version` 和 `data.version`）、目标 `data.version`、快照路径、当前阶段、出错信息、三个目录（私有状态目录、故障目录、临时目录）的当前位置及是否存在、执行者（进程标识和启动时间）、时间。
- 阶段：`migrating`（快照已校验，正在迁移）→ `restoring`（正在恢复，并记录已完成到第几步）→ 成功后**删除日志**。
- 日志在执行第一个迁移脚本**之前**写入。迁移全部成功、或恢复全部成功之后才删除。

**串行：同一插件同一伴侣同时只有一个操作**
- 迁移、恢复、解除恢复阻止，以及该插件的加载、启用、重新加载、停用、卸载，对同一伴侣的同一插件**串行执行**：用一把锁保护，锁同时在进程内和跨进程有效（例如锁文件 + 进程内锁），锁文件中记录持有者。
- 迁移或恢复进行中，对该插件的加载、重新加载等请求**不排队等待**，直接返回"迁移进行中"，不读取迁移日志、不触发崩溃恢复。
- 其他操作（加载、启用、重新加载、停用、卸载）进行中，后来的操作同样**不等待**，立即返回 `operation_in_progress`（附带正在进行的操作名称），由调用方决定是否稍后重试。重试时按新请求处理：带计划标识的操作重新校验计划，计划已失效就要求重新生成。
- 一次操作涉及多个插件时（例如连带停用、按依赖顺序启用），按插件 id 的固定顺序**尝试**获取全部锁；任何一把拿不到，就释放已拿到的锁，整体返回 `operation_in_progress`，不做任何部分修改。这样不会出现两个操作互相等待的死锁。
- 宿主自己的启动流程（伴侣启动时依次加载插件）也遵守同样的锁，但它是唯一的执行者，不会与自己冲突。
- 只有在拿到锁之后看到的迁移日志，才按下面的"加载时检查日志"处理。锁文件存在但持有者进程已不在时，视为持有者已崩溃，可以接管锁。

**版本记录在整个过程中不写入**
- `plugin-versions.json` 只在"迁移全部成功"后写一次新值。迁移或恢复过程中从不写它，所以也不存在"回退版本记录"这一步。
- 写入时只更新本插件在本伴侣下的那一项，不覆盖其他项。

**加载时检查日志**（伴侣启动、启用插件、重新加载插件）

| 日志状态 | 处理 |
|---|---|
| 没有日志 | 按 `plugins.md` 第 6.1 节正常比较版本 |
| 阶段为 `migrating`，版本记录仍是**旧**的 `data.version`（迁移途中崩溃） | 视为迁移失败，自动执行第 4.2 节的恢复，与运行中失败的处理相同 |
| 阶段为 `migrating`，版本记录已是**新**的 `data.version`（迁移已全部成功，写完版本记录、删除日志之前崩溃） | 迁移已完成：只删除残留日志并写审计记录，然后正常启动 |
| 阶段为 `migrating`，版本记录缺失或是其他版本 | 无法判断，进入"恢复未完成" |
| 阶段为 `restoring`，或自动恢复再次失败 | 状态为**"恢复未完成"**，见下 |

**"恢复未完成"状态**
- 插件不启动；必需依赖它的插件也不启动，可选依赖方收到"服务不可用"事件；本体、其他插件、其他伴侣照常运行。
- 拒绝：启动该插件、为它生成新的迁移计划、清理日志中引用的故障目录。卸载仍然可以执行（只是不再装配，数据和日志保留）。
- 宿主**不自动重试**恢复，避免反复失败。
- `status`（以后 WebUI 也是）持续显示一条**错误级**提醒：伴侣、插件、失败的阶段和原因、三个目录的当前位置、快照路径，以及下面两种处理方式。

**通用规则：不凭空创建私有状态目录**
只要该插件在该伴侣下已有版本记录，私有状态目录不存在时，宿主拒绝启动并报告"私有状态缺失"，**不新建空目录**。只有首次启用（没有版本记录）时才创建。这条规则同样适用于用户手动删除或移动了目录的情况。

**解除方式**（只能由用户发起，方式与连带停用相同：先生成只读计划，再带计划标识确认；计划生成后日志或相关目录变化时，计划失效）

1. **重新恢复**：计划列出将要执行的剩余步骤。执行前先重新校验快照；按日志记录的进度继续：
   - 私有状态目录还是迁移后的内容 → 整体改名为故障目录（名称已存在时加序号）；
   - 临时目录存在且校验通过 → 直接使用，否则重新解密快照；
   - 把临时目录改名为私有状态目录。
   全部成功后删除日志，插件进入普通的"迁移失败"状态（第 6.1 节：修好代码或用 Git 回到旧版本后即可启动）。任何一步失败就停止，保持"恢复未完成"，更新日志。
2. **接受当前目录**：用于快照本身损坏、或用户已经手动整理好目录的情况。前提：私有状态目录存在。计划中注明当前目录内容是否与快照一致（逐个文件比对哈希）；不一致时明确提示"该插件将使用与快照不同的数据"。确认后删除日志，插件进入"迁移失败"状态。

两种方式都写审计记录。

**解除时版本记录的处理**

版本记录正常（仍是迁移前的值）时，两种方式都不改动它。

版本记录缺失或异常（与日志中"迁移前的版本记录"和目标版本都对不上）时：
- **重新恢复**：数据回到快照，所以把版本记录写为日志中"迁移前的版本记录"。计划中列出"版本记录将从 X 改为 Y"。
- **接受当前目录**：宿主无法知道当前数据属于哪个版本，由用户在计划中**明确选择**：
  - 迁移前的数据版本（日志中的旧值）→ 写入旧值；之后代码仍是新版本时，插件回到"待迁移"；
  - 目标数据版本（日志中的新值）→ 写入新值，`version` 写为当前代码的版本；之后正常启动。
  - 没有默认选项；用户不选，计划不能确认。
- 日志本身损坏、读不出旧值和新值时：只能选"接受当前目录"，由用户输入一个数据版本（必须是 1 到当前代码 `data.version` 之间的整数），计划中显示警告"无法核对，该版本由用户指定"。
- 写入版本记录与删除日志的顺序：先写版本记录，再删除日志。两步之间崩溃时，日志仍为"恢复未完成"；用户再次执行同一解除方式即可（写入相同的值，结果相同）。

## 5. 实例目录的版本记录（可选）

实例目录不进入公开仓库。用户如果想用 git 记录记忆和设定的变化，可以把实例目录的一部分做成**单独的、只在本机的 git 仓库**（不设置远端），只跟踪文本内容：`AGENTS.local.md`、`docs/`、`companion.yaml`、`persona/`、`exports/*.jsonl`。数据库、凭据、资产、备份不进入这个仓库。具体做法由部署文档决定。
