# 插件系统

目标：所有功能都是模块化插件，可以按伴侣启用和配置，可以在创意工坊中浏览、安装、更新和卸载，依赖关系自动解析。

## 1. 插件包

```
plugins/<id>/
├─ plugin.json      清单
├─ __init__.py      入口：注册扩展点实现
├─ ...              实现代码
├─ data/            自带的公开静态数据
├─ migrations/      私有状态的升级脚本
├─ tests/           离线测试（使用 sdk.testing）
└─ README.md        创意工坊详情页内容
```

官方插件在仓库 `plugins/` 中；从创意工坊安装的插件放在 `CLYTIE_HOME/plugins/<id>/`。

## 2. 扩展点（contribution points）

插件的"类型"只是分类标签，真正决定插件能做什么的是它声明的扩展点。一个插件可以同时实现多个扩展点（例如睡眠插件同时有行为扩展、定时任务、服务、状态卡片）。

| 扩展点 | 作用 |
|---|---|
| `channel` | 接入一个平台 |
| `model` | 提供一个生成模型 |
| `embedder` | 提供文本向量（记忆检索用） |
| `tool` | 提供一个给模型调用的能力 |
| `behavior.<环节>` | 在消息流程的某个环节施加影响（见第 3 节） |
| `context_section` | 向上下文贡献一段内容（有预算） |
| `schedule` | 注册定时任务（由本体调度器驱动） |
| `service` | 向其他插件提供一个具名服务（如 `sleep.state`） |
| `event_subscriber` | 订阅事件总线上的事件 |
| `memory.retriever` / `memory.importer` / `memory.consolidator` | 记忆检索器、导入器（如旧系统导入）、经历整理器 |
| `memory.reranker` | 对已投影的候选记忆重排（memory-spec §4.4），通过 factory 装配 |
| `notifier` | 提供一种通知渠道（守护进程和边界保护用来通知主人） |
| `cli_command` | 新增一个 CLI 子命令 |
| `api_route` | 新增 API 路由（只读状态或插件自己的操作） |
| `webui_panel` | 在 WebUI 中提供状态卡片或页面 |
| `config` | 配置 Schema（WebUI 据此自动生成设置页） |

新增扩展点需要修改 SDK，按 `sdk.md` 的版本策略进行。

## 3. 行为环节

| 环节 | 用途 | 可返回的指令 |
|---|---|---|
| `message_received` | 消息进入后（已过过滤；可防重事件已防重，`dedupable = false` 的事件不经过防重，可能重复到达） | 无（只观察、记录） |
| `before_attention` | 决定回应方式 | 正常 / 只回表情 / 简短回应 / 不回应 / 改为某种模式（如呓语） |
| `attention` | 说话时机 | 回应 / 不回应 / 延迟 N 秒后再判断 |
| `after_generation` | 回复生成后 | 拆分 / 改为卡片 / 附加引用 |
| `before_send` | 交付前 | 调整交付形式（不能改内容、不能绕过出站检查） |
| `task_completed` | 任务交付后 | 无 |

规则：
- 同一环节按优先级执行，同优先级按插件 id 排序，结果可复现。
- 多个插件给出冲突指令时，按本体定义的合并规则处理（例如"不回应"优先于"正常"），合并规则写在 SDK 中并有测试。
- 边界检查和出站检查在所有插件之后执行，插件无法跳过。
- 插件出错时记录日志并按清单中声明的安全默认值处理，不影响本体和其他插件。

## 4. 清单 `plugin.json`

工具名不能以 `core_` 开头，该前缀保留给本体工具；清单校验拒绝此前缀（`agent-spec.md` §3.3）。

| 字段 | 说明 |
|---|---|
| `id` | 小写加连字符，全局唯一 |
| `name` / `summary` / `category` | 显示名称、简介、分类（能力 / 行为 / 平台 / 模型 / 记忆 / 工具） |
| `version` | 语义化版本 |
| `requires.sdk` | 兼容的 SDK 版本范围 |
| `dependencies` | `{id: 版本范围}`，可标记 `optional` |
| `conflicts` | 不能同时启用的插件 |
| `contributes` | 实现的扩展点及其参数（工具描述、环节优先级、服务名、定时规则……） |
| `permissions` | 需要的权限（第 5 节） |
| `config` | 配置的 JSON Schema 及界面提示 |
| `data` | 私有状态的版本号、卸载时的处理（默认保留） |
| `failure_default` | 出错时的安全默认值 |

能力插件的工具描述包括：何时使用、**何时不用**、正反例（含否定、转述、讨论三类）、参数 Schema、适用对象、是否重任务、风险、交付方式。

- 工具清单新增可选字段 `timeout_s`（正整数，秒）；截止时间计算与实例上限见 `kernel-spec.md` 第 8 节。
- 工具参数 Schema 支持 `"x-clytie-sensitive": true` 注解。任意层级的敏感属性写入账本前替换为 `"[redacted]"`；`oneOf` / `anyOf` / `allOf` 任一分支标为敏感就按敏感处理，详见 `kernel-spec.md` 第 13.2 节。
- 插件不把凭据写进 `ToolResult.data` 和收据的 `error.message`；这两处没有 Schema，不自动脱敏。

## 5. 权限

| 权限 | 含义 |
|---|---|
| `memory.read.public` | 读取当前场景可见的非私密记忆 |
| `memory.read.private` | 读取私密记忆（只在私聊场景生效） |
| `memory.write` | 写入或修订记忆 |
| `message.proactive` | 主动发起消息 |
| `message.react` | 表情回应 |
| `peer` | 使用伴侣通道 |
| `model.invoke` | 自行调用模型（计入额度） |
| `network` | 访问网络 |
| `assets.write` | 写入资产库 |
| `subprocess` / `gpu` | 启动子进程 / 使用 GPU |

官方插件在伴侣进程内运行，权限通过 `ctx` 的接口范围控制。第三方插件开放前，需要另行设计签名、审核和进程隔离（SDK 的可序列化约束就是为此预留）。

## 6. 依赖与生命周期

```
发现 → 校验清单 → 安装 → (按伴侣)启用 → 配置 → 运行 → 停用 → 卸载
```

- 启用前解析依赖：缺少时给出补齐方案，确认后一并启用；版本冲突或 `conflicts` 时拒绝并说明原因；依赖必须无环。
- 停用一个仍被其他已启用插件**必需**依赖的插件时，分两步：
  1. **计划**：只读查询，返回将被连带停用的全部依赖方（包括间接依赖方），按依赖倒序排列。未确认时不做任何改动。
  2. **确认后执行**：调用方带上计划的标识确认后，宿主按倒序依次停用依赖方，最后停用目标插件。计划生成后如果依赖关系发生变化，计划失效，必须重新生成。
- 每次连带停用写一条记录（目标插件、连带停用的插件、时间）。重新启用目标插件时，宿主提示"上次连带停用了这些插件"，用户可以选择一并恢复。
- 本体模块不能停用，也不会被连带停用。
- 可选依赖方不阻止停用，只会收到"服务不可用"事件，继续运行。
- 配置按伴侣保存；支持热加载的插件立即生效，否则提示重启该伴侣。
- 升级规则见第 6.1 节。
- 卸载默认保留私有状态和它写入的记忆；彻底清除需要用户单独确认，且只删除该插件自己的目录。
- 本体模块在创意工坊中显示为"本体"，不能停用或卸载。

### 6.1 升级

**代码由外部更新，宿主只管数据。**

- 宿主**不安装、不移动、不替换、不删除**插件代码。
  - 仓库 `plugins/` 中的官方插件由 Git 管理（用户自己 `git pull` 或切换分支）。
  - `CLYTIE_HOME/plugins/` 中的插件以后由创意工坊安装器更新。安装器另行设计，任何情况下不触碰仓库 `plugins/`。
  - A2 不提供"新包放在独立目录再切换"的升级入口。
- 宿主为每个伴侣记录每个插件**上次成功运行时**的 `version` 和 `data.version`，保存在 `companions/<companion-id>/plugin-versions.json`。这个文件只有宿主能读写，不在插件私有状态目录内，也不在升级快照范围内。

每次加载插件时（伴侣启动、启用插件、重新加载插件），宿主比较清单和记录：

| 情况 | 处理 |
|---|---|
| 没有记录（首次启用） | 正常启动，写入记录 |
| 两个版本都相同 | 正常启动 |
| `version` 变了，`data.version` 相同 | 照常做兼容性检查（SDK、依赖、冲突），通过后直接启动并更新记录，写一条"已更新：旧版本 → 新版本"事件。不需要确认 |
| `data.version` 变大 | 不启动，状态为"待迁移"（见下） |
| `data.version` 变小（代码回退到更旧的版本） | 不启动，状态为"数据版本高于代码"。提示更新代码，或从升级快照恢复。不做降级迁移 |
| 缺少需要的迁移脚本 | 不启动，状态为"缺少迁移"，列出缺少的步骤 |
| 存在迁移日志，或私有状态目录缺失 | 先按 `data-and-backup.md` 第 4.3 节处理，优先于本表其他各行 |

- 没有启动的插件按停用处理：必需依赖它的插件也不启动（状态中注明原因），可选依赖方收到"服务不可用"事件，本体和其他插件照常运行。这些情况都**不改写**伴侣配置中的 `enabled`。
- 宿主运行期间代码被更新时，宿主不监视文件变化。新代码在下次加载该插件时才生效，并按上表比较。

**待迁移**分两步执行，方式与连带停用相同：

1. **计划**（只读）：列出伴侣、插件、`data.version` 从几到几、将依次执行的迁移脚本、快照保存路径。
2. **确认后执行**：调用方带上计划标识确认。计划生成后，如果插件代码或私有状态发生变化，计划失效，必须重新生成。执行顺序：
   1. 确认插件没有在运行。
   2. 按 `data-and-backup.md` 第 4.2 节生成快照并校验。
   3. 依次执行迁移脚本。
   4. 全部脚本成功即为**提交点**：依次写入版本记录 → 删除迁移日志 → 启动插件。
   - 启动失败不回滚数据：新数据和新版本记录保留，按普通的"启动失败"处理（SDK 规格第 7.1 节）。原因：启动可能已经产生无法撤回的外部影响（发消息、访问网络）；而且新数据本身已经完整迁移，问题出在代码上。
   - 用户确实需要回到旧数据时，可以用本次的升级快照手动恢复（快照按 `data-and-backup.md` 第 4.2 节保留）。

多个伴侣使用同一个插件时，一份计划可以列出多个伴侣，但每个伴侣独立执行、独立恢复，一个失败不影响其他伴侣。

**迁移失败**时：
- 按 `data-and-backup.md` 第 4.2 节恢复该插件的私有状态。
- 版本记录保持旧值；插件保持"迁移失败"状态，不启动；报告失败的脚本和原因。
- 宿主不回退代码。用户修复代码，或用 Git 回到旧版本后，下次加载时重新比较。回到旧版本时，`data.version` 与记录相同，旧代码可以直接启动。

## 7. 创意工坊

- 索引 `plugins/catalog.json` 由各插件清单生成（id、版本、简介、分类、依赖、权限、更新说明）。
- 先只提供官方插件；格式按以后可以加入第三方来源设计（来源地址、签名字段预留）。

## A4.3 在线备份支持（待实现）

以下为已批准的 A4.3 契约，尚未实现、未经验收；完整依据为 `backup-spec.md`，不代表历史里程碑已提供这些能力。

这是在线备份要求下的新公共契约，须先同步 sdk-spec、清单 Schema 和 CHANGELOG，再实现。插件仍只 import clytie.sdk。
清单新增可选 `backup`：`mode` 为 `stateless | snapshot | unsupported`；省略按 unsupported。snapshot 模式需在 `contributes` 声明唯一 `backup.snapshot` factory，按现有 factory 约定返回提供者；其他模式不允许声明。stateless 表示没有需恢复的业务持久状态，宿主发现 plugin-data 内非声明缓存数据时拒绝该结论并报缺项。缓存不能由插件临时声明来掩盖已有业务数据。
已停止且无活跃执行者/恢复日志的插件，可在取得原生命周期及数据锁后做离线一致复制；无需为备份启动插件。运行中的 unsupported 插件有状态时为缺项。支持状态在列表、启用计划及 status 展示，旧插件仍能正常启用，不把新增字段变成隐式停用。

公共协议（以下 ticket/handle 是进程内对象，不持久化或跨 IPC 序列化）：

```
async prepare(request: BackupRequest, cancel: CancelToken) -> BackupTicket
async capture(ticket: BackupTicket, epoch: str, cancel: CancelToken) -> BackupView
async materialize(view: BackupView, sink: BackupSink, cancel: CancelToken) -> None
async release(ticket: BackupTicket) -> None
```

- `BackupRequest`：operation_id、companion_id、plugin_id、目标 data_version、准备 deadline；这些由宿主填充。提供者不自行选择其他实例/伴侣。
- prepare 在捕获门闩外准备资源，可在私有临时区域工作，不停止插件、发送消息、调用模型或改变业务事实；默认 10 秒。capture 在组捕获窗口内固定该 epoch 的稳定视图，不能在这里做大文件复制。准备期间业务改变时须重新验证，不允许返回旧快照却标上新 epoch。
- `BackupView`：epoch、data_version、revision（提供者的稳定版本标识）以及提供者私有只读句柄。提供者保证 materialize 对应 capture 版本；宿主验证 epoch/版本、完整成员和关联，无法证明则不能算完整。实现允许不可变版本、数据库读视图等方式，不要求所有插件采用同一种存储。
- `BackupSink` 只允许 `async write(relative_path: str, chunks: AsyncIterator[bytes]) -> BackupEntry`。宿主计算字节数与哈希；返回相对路径、size、sha256。路径限定当前插件备份命名空间，拒绝重复/穿越/链接，不把任意宿主文件句柄交给插件。sink 拒绝写入声明为凭据的内容；内容完整性仍由插件契约和测试保证，不以扫描代替。
- materialize 在门闩释放后运行，只读稳定视图；取消/超时后不再接受其迟到写入。release 在成功、失败、取消时均执行且应幂等，默认 2 秒；记录释放失败，不吞掉它导致的资源泄漏。迟到资源继续被跟踪，不能把失去跟踪的 provider 说成已结束。
- 该接口提供备份快照，不授予通用恢复执行脚本权限。每个 sink 相对路径精确映射到恢复目标 companions/<cid>/plugin-data/<pid>/ 下的同一相对路径；成员必须是同一 data_version 可直接加载的完整持久布局。数据库须输出可直接打开的一致数据库文件，不接受需要执行 SQL 导入脚本、反序列化可执行对象或运行转换程序才能还原的逻辑导出。需要转换的 provider 本阶段视为 unsupported，结果 partial。宿主只做安全文件重建和格式校验，插件只在用户后来正常启动时按原生命周期加载。

## Issue #72：capture 回调重入（用户已确认）

backup.snapshot.capture 不得重入被屏障暂停的本体存储队列，须按 sdk-spec 的异步调用链规则检测；所需读取放在 prepare，capture 核验版本变化，不能用旧视图改标 epoch。违规列缺项，不为成功捕获杀插件或关闭隔离。插件停止回调的合法存储收尾由 storage-spec.md 的所有者生命周期保留，插件 API 权限不扩大。
