# 真实冒烟测试工具规格（B5）

状态：用户已确认（2026-11-18，PR #122）；§5、§6 的判定补充为草案，待用户确认（Issue #123）。

用户手动测试每次只适合一两条。冒烟测试工具用一个专门的测试账号，按固定用例向测试会话发消息，从平台侧观察伴侣的回复和状态表情，再从本机 API 读取账本侧的结果，生成报告。它代替 B2b 的真实测试观察脚本。

## 1. 范围

- 只做 qq-onebot 一个驱动；接口留出平台无关的部分（用例、判定、报告），以后可以加别的驱动。
- 用例由用户写好，工具原样发送，**测试方不调用模型**，结果可复现。按剧本由模型生成说法的"模拟用户模式"不在本期（roadmap 阶段二待办）。
- 不做：并发发送、压力测试、定时自动运行、WebUI 页面。

## 2. 组成

| 部分 | 位置 | 说明 |
|---|---|---|
| 测试账号 | 用户准备 | 专门的 QQ 号，不是伴侣账号，也不是 owner 主号 |
| 测试方协议端 | 单独的 NapCat 容器 | 与伴侣的协议端分开，只监听本机端口 |
| 工具 | `src/clytie/smoke/`，命令 `clytie smoke run` | 读取配置和用例，驱动测试方协议端，调用本机 API |
| 配置 | `$CLYTIE_HOME/smoke/smoke.yaml` | 测试方 WS 地址、令牌文件、测试账号的逻辑 ID、被测伴侣、上限 |
| 用例 | `$CLYTIE_HOME/smoke/cases.yaml` | 私有，可能含用户自己的说法；仓库只放虚构示例 `examples/smoke/cases.yaml` |
| 报告 | `$CLYTIE_HOME/smoke/reports/<时间>.json` | 私有；终端只输出通用摘要 |

测试账号在实例配置 `people` 中登记为一个逻辑人物（如 `smoke_tester`，角色 `member`），并加入 `test_conversation` 的 `members_expected`。不登记为伴侣。

**更换测试号**（测试号被风控时）：工具和用例只认逻辑 ID，不认号码。

- 备用号：在同一个逻辑人物的 `accounts` 下再登记一个号，并提前拉进测试群。测试方协议端换成备用号登录后即可运行，不用改工具、用例和伴侣配置。
- 换新号：在 `accounts` 中替换号码，把新号拉进测试群，再让测试方协议端用新号登录。
- 旧号不再使用时从 `accounts` 中删掉，并移出测试群；否则成员检查仍把它算作测试人物。

## 3. 用例

```yaml
cases:
  - id: chat_basic
    text: "（虚构的打招呼）"
    expect: {reply: true, image: false, reactions: none}
    timeout_s: 60
  - id: draw_plain
    text: "（虚构的画图请求）"
    expect: {reply: true, image: true, reactions: [accepted, running, done]}
    timeout_s: 300
  - id: edit_last
    text: "（虚构的改图请求）"
    expect: {reply: true, image: true, reactions: [accepted, running, done]}
    timeout_s: 300
```

- `text` 原样发送；`mention`（默认 `true`）在开头加 @伴侣。
- `expect.reactions`：`none` 表示不应出现状态表情；列表表示依次出现的状态，最后一个必须是消息上**最终唯一**的表情。中间状态可以被规则跳过时，用 `optional:` 前缀标出（例如 `optional:running`）。
- 用例按顺序一条一条执行：上一条判定结束后才发下一条。

## 4. 运行流程

1. **离线检查**：读取配置和用例并校验；统计条数和预计图片数（`expect.image: true` 的条数）。超过 `limits.max_cases`（默认 10）或 `limits.max_images`（默认 4）时拒绝运行。
2. **当次同意**：显示伴侣、条数、预计图片数，要求输入 `y` 确认。`--yes` 不跳过这一步（AGENTS.md 3.2）。
3. **被测伴侣检查**：通过本机 API 确认被测伴侣正在运行、平台在线、准入不是关闭状态。否则停止。
4. **成员检查**：用 OneBot 标准接口 `get_group_member_list` 读取测试会话的成员，每个成员都必须能映射到 `members_expected` 中的人，并且当前登录的测试号和被测伴侣都在群里。不通过就停止，不发送任何消息。只报告"通过 / 不通过"和人数，不输出账号。
5. **账号核对**：`get_login_info` 的账号必须是测试人物 `accounts` 中的某一个；报告只写"第几个账号"，不写号码。
6. **逐条执行**：发送用例消息，记录它的 `message_id` 和发送时间，然后观察（第 5 节），直到判定结束或超时。
7. **任意一条失败立即停止**，不再发送后面的用例。
8. 写报告，输出摘要。

## 5. 观察与判定

**平台侧**（测试方协议端收到的事件）：

- 回复：按账本归属，不按"第一条"（Issue #123）。先用用例消息的 `message_id` 在账本摘要中找到对应记录（第 6 节的入站平台消息编号）；这条记录每一条 `sent` 交付的出站平台消息编号，在平台侧都必须收到伴侣发出的同一编号的消息。这些消息合起来就是本条用例的回复，一条回复可以由多条消息组成（例如先文字、后单独的图片）。记录每条消息是否含文字、是否含图片段和到达时间。
- 用例进行期间，伴侣在测试会话中发出、却不属于这条记录的消息，判为 `unattributed_reply`，用例失败。
- 状态表情：测试方收到的 `group_msg_emoji_like` 通知中，`user_id` 是伴侣账号、`message_id` 是用例消息的那些（qq-onebot-compat §2.2）。按到达顺序记录 `emoji_id`、`is_add` 和时间，用伴侣部署配置中的 `emoji_ids` 换回状态名。
- 最终表情只按平台侧通知判定，账本收据不能证明撤销成功（compat §2.1 允许撤销失败后照常添加，添加仍为 `sent`）。按添加和撤销通知推算消息上剩下的表情，结果分三种：
  - `verified`：每一次被替换的表情都收到了伴侣的撤销通知（`is_add: false`），推算结果只剩最后一个状态的表情；
  - `failed`：通知显示剩下不止一个表情，或者剩下的不是最后一个状态的表情；
  - `unverified`：应有的撤销通知没有收到（可能是协议端不推送、延迟或撤销失败，工具不区分）。
- 最后一个状态的添加通知到达后，再等 `min_interval_seconds` + 3 秒收集迟到的撤销通知，然后定结果。

**账本侧**（本机 API，第 6 节）：执行状态、交付状态、收据、状态回应、模型用量和错误码。

**一条用例通过**需要同时满足：

- `expect.reply` / `expect.image` 与观察一致；
- 状态表情的顺序与 `expect.reactions` 一致（以平台侧添加通知为准；收不到添加通知时用账本侧状态回应的收据，并在报告中注明来源）；`none` 时没有任何状态表情；
- 最终表情为 `verified`；为 `unverified` 时，本条用例结果是 `needs_visual_check`，不算通过也不算失败，不触发"失败即停"；
- 账本侧所有收据为 `sent`，没有模型错误；
- 在 `timeout_s` 内完成。判定在以下条件都满足后结束：记录的执行状态和全部交付都到了终态，每条 `sent` 交付都在平台侧收到，最终表情已经定结果（`none` 时回复全部收到后再等 `min_interval_seconds` + 2 秒，确认没有状态表情）。
- 交付为 `failed` 或 `unknown`，或者 `sent` 交付在 `timeout_s` 内没有在平台侧收到，用例失败。

**整次运行的结果**：

- 全部用例通过：`passed`。
- 有用例失败：`failed`，后面的用例不再发送。
- 没有失败，但有 `needs_visual_check`：运行结束时列出这些用例（只写用例编号），要求用户目视确认这些消息上只剩一个表情并输入 `y`。确认后为 `passed`，报告中这些用例记 `visual_confirmed: true`；不确认为 `failed`。`--yes` 不跳过这一步。

## 6. 本机 API：测试会话的记录摘要

新增只读路由 `GET /companions/<cid>/smoke/records?since=<ISO 时间>`：

- 只返回会话是实例 `test_conversation` 的记录；没有配置 `test_conversation` 时返回 `409 no_test_conversation`。
- 每条记录只含：`trace_id`、`kind`、`tool`、`exec_status`、`delivery_status`、入站平台消息编号、各交付的状态、错误码和出站平台消息编号（来自收据，没有时为 `null`）、状态回应的状态和收据、`model.usage` 的 token 合计、`reaction_outcome`、创建时间。平台消息编号只用于和平台侧对应，不写进报告。
- 不返回消息原文、参数、结果、人设和账号。
- 需要本机 API 登录，不需要确认，不写审计以外的任何状态。

## 7. 安全

- 只向 `test_conversation` 发送；目标会话在发送前再核对一次。
- 测试方令牌和本机 API 令牌从文件读取，不写进日志和报告。
- 终端和报告的公开部分不含账号、群号、消息原文和回复内容；报告中的回复只记录"有无文字、有无图片、字数"。
- 工具不读伴侣的记忆、人设和聊天记录，只用第 6 节的摘要。

## 8. 报告

```json
{"started_at": "...", "companion": "companion_a", "result": "passed|failed|stopped",
 "cases": [{"id": "draw_plain", "result": "passed", "reply_s": 65.0,
            "reactions": [["accepted", 0.0], ["running", 2.3], ["done", 60.0]],
            "final_reaction": "done", "receipts": ["sent"], "tokens": {"input": 1200, "output": 80},
            "failure": null}]}
```

终端摘要：每条用例一行（编号、结果、耗时、表情顺序），最后一行是总 token 数和图片数。

## 9. 验收

1. 离线：假测试方协议端 + 假伴侣（B4b 的离线端到端夹具），覆盖用例全部通过、回复缺图、表情顺序不对、最终剩两个表情、超时、收据失败各一个测试；任意一条失败后不再发送。
   - 回复归属：先文字、后不带引用的图片，两条都归到同一用例并判为有图；用例期间伴侣多发一条不属于该记录的消息，判 `unattributed_reply`；`sent` 交付在平台侧收不到时失败。
   - 最终表情：撤销通知齐全为 `verified`；撤销失败但添加成功（账本仍为 `sent`）、且没有撤销通知时为 `unverified`，整次运行要求目视确认，确认与不确认各一个测试；撤销通知显示剩两个表情时失败。
2. 上限超出、未确认、伴侣未运行、成员检查不通过、账号不符时都不发送任何消息，各有测试；测试人物有两个账号时，用任一个登录都能通过账号核对。
3. 第 6 节路由：只返回测试会话的记录；不含原文、参数、结果和账号（用虚构的敏感字符串断言不出现）。
4. 报告和终端输出不含账号、群号和消息原文。
5. 双平台 CI 通过；真实平台连接和模型调用次数为 0。
6. 真实运行由用户当次同意后执行一次（3 条用例），结果与用户目视一致。

规模预估：1–1.5 天。
