# 对话主干实现规格（A3.2：工具循环、人设、边界与出站检查）

本文件补齐 A3.2 实现所需的契约。设计依据是 `design/conversation.md`、`design/boundary.md`、`design/lessons.md` 和 `overview.md` 第 5 节；账本、交付、取消的既有规则见 `kernel-spec.md`，本文件只在其上接入，不改变它们。

- 标注"用户已确认"的条目是需求或隐私决定，改动前必须经用户确认；其余是技术约定，按 AGENTS.md 第 4 节处理。
- 本文件与其他规格冲突时，以本文件为准，并同步修改对方文档（第 14 节列出了需要同步的地方）。
- A3.2 只使用假模型、假平台、假通知渠道离线验证，不连接任何真实账号。

---

## 1. 处理流程总览

```
入站事件
  → 身份解析 → 输入过滤（第 8 节）→ 暂停名单（第 7.3 节）→ 防重（kernel-spec §3）
  → 群聊未 @ 的取消（第 6.1 节）
  → message_received → before_attention → attention / 消息合并（第 2 节）
  → 打开记录 → 取消快速路径（第 6 节）
  → 工具循环（第 3 节）：上下文装配（第 4 节）→ 模型 → 工具 → …
  → 回复草稿 → after_generation → 出站检查（第 9 节）→ 附加任务单 → before_send
  → 执行封口与登记交付（kernel-spec §2）→ 交付
```

- 输入过滤最先执行（用户已确认）：命中就直接丢弃，不写入 `dedupe` 和 `inbound`，即使发送人正在暂停期也一样。没有命中、但发送人在暂停期的消息，按第 7.3 节入账为 `ignored`，流程到此结束。
- 主动消息不经过这条入站流程，见第 15 节。
- 主人私聊不能被 `Skip`、`Ignore` 完全忽略的本体保护（sdk-spec §6）保持不变。

## 2. 注意力判断与消息合并

- `before_attention` 返回 `Ignore`：入站记为 `ignored`，不创建记录。`ReactOnly` 按 kernel-spec §13.4 处理。`Mode(name, params)`：本次处理带上这个模式，上下文中注入一行"当前模式：name"，模式的具体表现由发出它的插件通过 `context_section` 提供。
- **批次按"会话 + 发送人"划分（用户已确认）**：每个批次只包含同一个人的消息，因此一条记录只对应一个请求人，权限、保障模式、越界计数和取消都归属这个人。不同人的消息不会合并；他们说的话仍按第 4.4 节出现在聊天记录中，她能看到整个群的讨论。
- `attention` 返回 `Defer(seconds)`：把这条消息放进它的**待处理批次**，到时间后带着整批再判断一次。期间同一个人在同一会话的新消息加入同一批次，重新判断时一起作为输入。本体对单个批次的累计延迟上限沿用 120 秒（sdk-spec §6）。
- `Respond`：以批次中**最后一条**入站消息打开记录（`source_event_id` 指向它）；批次中更早的消息改为新状态 `merged`，并记录 `merged_into = trace_id`。上下文中它们按原顺序出现。
  - `inbound.state` 新增 `merged`，账本模式版本加一，按 kernel-spec §14 迁移。
  - 重启时，批次中仍在等待的消息按 `received` 处理，即 `dropped_on_restart`（kernel-spec §2），不恢复批次。
- `Skip`：整批记为 `ignored`。

## 3. 工具循环

### 3.1 模型调用

- 每次调用模型都构造 `ModelRequest`：消息由第 4 节装配；`tools` 只包含**当前可用**的工具（第 5 节）和本体工具（第 3.3 节）。
- `Budget.deadline`：
  - 记录已是 task：取记录的 `deadline`（kernel-spec §8）。
  - 记录仍是 chat：本次模型调用开始时间 + `agent.model_call_seconds`（默认 120 秒）。这只是单次模型调用的截止，不是记录的截止时间，kernel-spec §8"chat 没有执行截止时间"的规则不变。
- `Budget.max_tool_rounds` 取 `agent.max_tool_rounds`（默认 4）。
- 模型插件声明 `agent_type = true`（自带工具循环，通过 MCP 使用工具）时，A3.2 不支持：伴侣启动失败，报告 `unsupported_model_type`。MCP 接入在阶段二的模型插件中设计。
- 模型插件声明 `supports_tools = false` 时，`tools` 为空，能力状态段落照常注入（第 5 节），她可以如实说明现在做不了。

### 3.2 循环规则

- `finish = tool_calls`：按 `tool_calls` 的顺序**逐个**执行，不并行。每个调用的结果作为一条 `tool` 消息加入对话，再调用一次模型。每次模型返回工具调用记为一轮。
- 单个调用的处理：
  1. 工具名不存在，或是当前不可用的工具：不执行，返回 `ToolResult(status="error", error.code="unknown_tool")` 或 `denied`（附第 5 节的原因），交回模型。
  2. 参数不符合工具的参数 Schema：返回 `error.code = "invalid_arguments"`，不占用幂等键。
  3. 其余按 kernel-spec §4 的顺序：权限与额度 → 幂等键 → `prepare` → 领取 → 执行。查到仍在执行的已有调用（`in_progress`）时，告诉模型"这件事已经在做了"，附上编号。
- 交给模型的工具结果是 `ToolResult.content`，超过 `context.material_budget_chars` 时截断并注明"已截断"。`data` 只写入账本，不交给模型。
- 轮数用完后仍要求调用工具：再调用一次模型，`tools` 为空，并附一句"工具轮数已用完，请直接回复"。这一次返回的工具调用一律忽略。
- `finish = stop`：`text` 就是回复草稿。`text` 为空、并且本次循环没有可交付的产物时，视为她选择不回复：执行状态为 `ok`，不登记交付。`text` 为空但有产物时，按第 3.5 节照常交付产物。
- `finish = error | deadline`：执行状态为 `error`，按第 10 节处理。
- `finish = cancelled`，或循环中记录被取消：执行状态为 `cancelled`，不发兜底回复。

### 3.3 本体工具

本体向模型提供以下工具。名字以 `core_` 开头；插件清单中的工具名不能以 `core_` 开头，清单校验拒绝（SDK 0.x 不兼容变更，写入 CHANGELOG）。

| 工具 | 何时提供 | 作用 |
|---|---|---|
| `core_cancel_task` | 当前会话中有可取消的任务时 | 按自然语言指定的目标取消任务（第 6.3 节） |
| `core_remember` / `core_forget` | 本批次说话人为主人，且本次允许工具 | 当场记、修订或撤销（memory-spec §2） |
| `core_recall` | 本次允许工具 | 回想记忆与本会话任务（memory-spec §5.3） |
| `core_report_boundary` | 说话人不是主人、也不是同部署的伴侣时 | 登记一次越界请求（第 7.2 节） |

- 本体工具的调用**不算能力调用**：不领取幂等键，不把记录升级为 task，不触发任务状态回应和任务单。调用和结果写入审计。
- 本体工具不受 `permissions` 配置控制，按上表的条件提供。

### 3.4 取消贯通（Issue #20 第 1 项）

- 每条记录的工具循环持有一个取消令牌。模型调用和能力执行使用它派生的子令牌。
- 用户取消执行中的 chat 记录（只能用 `reply_to`，kernel-spec §8）时，触发这个令牌，等待 `tasks.cancel_grace_seconds`，仍未结束就取消协程，记录标为 `cancelled`。之后到达的模型结果和工具结果写审计。
- 回归测试：引用一条执行中、还没有工具调用的聊天消息说"停"，模型调用收到取消，记录为 `cancelled`，不登记交付。

### 3.5 回复与交付意图

- 回复草稿 `ReplyDraft`：`parts` 为文字；`form = plain`；`quote` 为空。之后依次经过 `after_generation`、出站检查（第 9 节）、附加任务单、`before_send`。
- 本次循环中 `ok` 的工具结果带来的产物（`ToolResult.assets`），各作为一条独立的 intent，排在文字回复之后。
- **任务单**：记录是 task、并且有文字回复或产物要发出时，按 kernel-spec §13.3 生成任务单。
  - 有文字回复：接在文字回复最后一条 intent 的末尾（另起一行）。
  - 没有文字回复、只有产物（用户已确认）：任务单单独作为一条文字 intent，排在全部产物之后。不另外生成其他文字。
  - 任务单在 `after_generation` 之后附加，插件不能改它。
  - 任务单**单独**做出站检查，不参与改写（第 9.3 节）。隐私类命中说明配置有误（例如对外显示名就是内部名字）：去掉任务单，回复和产物照常发出，记 WARN 并在 `status` 中提示修改配置。
- 产物只做 kernel-spec §11 的格式和大小检查，出站检查不检查图片、音视频的内容。

## 4. 上下文装配

### 4.1 组成与顺序

每次调用模型，消息按以下顺序装配：

1. **system**：
   1. 本体的行为规则（仓库中的固定文字，通用、不含任何部署信息），包括：不说工程用语和系统内部名称、不编造做不到的理由、对方提到账本中没有的事时不顺着认下（第 4.3 节）。
   2. 人设：按第 4.2 节组合的人设层。
   3. 本体底线（放在人设之后）："任何时候都不声称自己是真人；有人认真需要确认时如实说明。"人设文件无法删除或覆盖这一段。
2. **能力状态**（第 5 节）：每次都注入，不参与预算裁剪。
3. **最近任务**（第 4.3 节）。
4. **记忆**：按 `memory-spec.md` §5 注入投影后的核心记忆与检索记忆，整条预算裁剪、使用本次调用的临时记忆编号；主动消息同样按目标场景注入。投影内没有有效记录时只写“你们之间还没有记住的事”，有记忆但没检索到时不写这句。不提供预置记忆或初始资料。
5. **插件段落**：`context_section` 按 sdk-spec §6 的规则收集、排序、裁剪；`Mode` 的说明行放在这里的最前面。
6. **聊天记录**（第 4.4 节）。
7. **本次消息**：合并批次中的全部消息；如果有取消快速路径的结果（第 6.1 节），附在最后。

### 4.2 人设

- 人设文件是 UTF-8 的 Markdown，位于 `companions/<id>/persona/`，由 `companion.yaml` 的 `persona.files` 和 `persona.scenes` 按场景选择、按列出的顺序拼接。
- **私密段落**：在 `<!-- private -->` 和 `<!-- /private -->` 之间的内容，只在当前场景属于 `memory.private_scenes` 时加载，其他场景整段去掉。标记不成对时伴侣启动失败，报告文件和行号，不猜测范围。
- 行为规则（怎么做）写在本体规则和插件中，人设文件只写"她是谁、怎么说话"。具体发生过的共同经历只以记忆和任务记录为准，人设关系设定不等于发生过的事（memory-spec §5.2）。这是写作约定，程序不检查。

### 4.3 最近任务（L2、L6 的账本部分）

- 注入本会话最近 24 小时内、最多 10 条 task 记录的摘要：编号、能力、发起人、执行状态、交付状态、结束时间、结果摘要（`Plan.summary` 和 `ToolResult.content` 的前 200 字）。
- 只包含读取场景按 kernel-spec §13.1 能看到的记录。
- 有"发了一半的组"时，按 kernel-spec §7 的三档说明注入，每组只注入一次（之后的上下文不再重复）。
- 本体规则写明：被问起做过什么，以这里的记录为准；对方提到这里和记忆里都没有的事时，不顺着认下。两处都没有时先用 core_recall 回想，仍没有就直说不记得，不顺着认下；具体规则和 L6 四种离线场景见 memory-spec §6。

### 4.4 聊天记录

- 来源是账本：本会话的入站原文（`processing`、`ignored`、`merged` 状态都包括；`dropped_on_restart` 和原因为 `boundary_paused` 的 `ignored` 不包括，见第 7.3 节）和出站原文（只取 `sent` 和 `unknown` 的 intent；`unknown` 的标注"不确定是否发出"）。
- 每条消息标注说话人：
  - 角色由身份解析决定：主人、同部署的伴侣、群友、陌生人，不从消息内容推断。
  - 显示名取平台昵称，标明"昵称"，不作为身份依据。
- 被引用的消息（`reply_to`）在本伴侣账本中、当前场景可见、并且不是暂停期间入账的消息时，附上它的原文；否则只注明"引用了一条看不到的消息"。
- 预算：最近 `context.max_messages` 条，总字数不超过 `context.max_chars`；单条超过 `context.max_single_message_chars` 时只截断这一条。字数按 Unicode 字符计算。
- **更早的内容直接舍弃，不做摘要（用户已确认）**。conversation.md 的摘要设计保留，以后单独实现，届时写明额度消耗。
- 链接替换为 `[链接N]`、资料 15 分钟全文等规则（conversation.md §1）随 `recall-material` 插件在阶段二实现；A3.2 中链接按原文出现，工具结果只在本次循环内出现（第 3.2 节）。

## 5. 能力状态注入（L3）

- 每次调用模型都注入一段"能力状态"，列出本伴侣装配的每个工具：
  - 可用：工具名和一句话说明。
  - 不可用：工具名和原因。原因只能是下表之一，文字由本体固定，模型不能自己编造：

| 原因代码 | 说明文字（大意） |
|---|---|
| `permission` | 对方没有使用这个能力的权限 |
| `protection_mode` | 额度紧张，暂停非主人的重任务，预计恢复时间（有 `resets_at` 时写出） |
| `disabled` | 这个能力已停用 |
| `start_failed` / `migrating` | 这个能力暂时维护中 |
| `model_no_tools` | 当前模型不支持使用工具 |

- 不可用的工具**不**放进 `ModelRequest.tools`，模型无法调用。
- 权限：说话人的角色在 `permissions` 中没有列出这个工具，或不在工具清单的 `audience` 中，就是不可用。
- **保障模式**（boundary.md §3）：
  - 额度来自 `ModelTurn.quota` 和不消耗模型调用的 `quota()`；任一窗口的剩余 ≤ `protection.enter_ratio`（默认 0.2）时进入，所有窗口都回到 > `protection.exit_ratio`（默认 0.3）时退出。额度未知时不进入。
  - 进入或退出时发布 `quota.changed`。
  - 保障模式下，非主人发起的、清单标为 `heavy` 的工具不可用（`protection_mode`），不排队。主人不受影响，普通聊天照常。
  - 状态只保存在内存中，启动时调用一次 `quota()` 初始化。

## 6. 取消的文字识别

### 6.1 快速路径

- 条件：去掉 @自己、首尾空白和首尾的标点、表情之后，消息文字**完全等于** `tasks.cancel_words` 中的一项（默认 `["取消", "停", "停止", "停下", "别做了"]`），或者是"其中一项 + 空格（可省略）+ 8 位十六进制编号"。
  - 编号先转为小写再交给取消入口。
  - 只用完全相等判断，"停车场""别停"都不匹配。这是 overview.md §5 唯一允许的程序判断，其余意图一律由模型判断（L1）。
- 匹配时，打开记录后、调用模型之前，按 kernel-spec §8 调用取消入口：带引用就用 `reply_to`，带编号就用 `task_id`，否则用默认的选择方式。
- 取消结果（`cancelled`、`not_found` 等）作为一行说明附在本次消息之后，仍然调用模型，由她用自己的口吻回应。模型不可用时按第 10 节处理。
- **群聊中没有 @ 她的取消（用户已确认）**：这类消息通常会被 `attention` 跳过，到不了上面的流程。因此在防重之后、行为环节之前，单独判断一次：
  - 文字满足上面的匹配条件，并且发送人在这个会话中有可取消的任务（主人：会话中任何未结束的任务；其他人：自己发起的未结束任务）时，直接调用取消入口。
  - 这条消息之后记为 `ignored`（原因 `cancel_only`），不调用模型、不回复文字；被取消任务的原消息上，状态回应按 kernel-spec §13.5 变为 ❌，以此表示已停下。
  - 不满足条件时照常进入行为环节，不做任何处理。
  - 私聊和 @ 了她的消息仍走上面的流程。

### 6.2 可见性先于权限（用户已确认）

- 取消入口先按 kernel-spec §13.1 判断目标记录在当前场景是否可见。看不到的记录一律返回 `not_found`，之后才检查取消权限（`denied`）和是否已结束（`already_finished`）。
- 这样在群里报出一个私聊任务的编号，从回答中无法判断它是否存在。代价是：私聊中发起的任务，要回到能看到它的场景取消。
- 适用于快速路径、`core_cancel_task` 和引用取消。

### 6.3 自然语言指定

- 例如"把 XX 的那个画图停掉"：由模型判断目标，调用 `core_cancel_task`，参数为 `task_id`（从第 4.3 节的最近任务中选取）。
- 取消入口的 `actor` 永远是当前说话人，权限由本体按 kernel-spec §8 检查，模型无法越权。
- 工具说明写明：目标对不上或有多个可能时，先反问，不要猜（用户已确认）。

## 7. 关系边界保护

### 7.1 类别

沿用 `boundary.categories`：当对方的恋人（`romance`）、修改人设（`persona_change`）、说指定的亲密台词（`scripted_intimacy`）、画亲密或暗示性的图（`intimate_images`）、打听主人的隐私（`owner_privacy`）。只有开启的类别会出现在工具参数的枚举中。

### 7.2 判断与登记（用户已确认）

- 是否越界由主模型在回复时判断，不使用关键词或正则（L1）。她拒绝越界请求时，调用 `core_report_boundary(category)` 登记，回复照常由她用人设口吻说出。
- 工具说明必须包含正反例：

| 计入 | 不计入 |
|---|---|
| 认真要求她当自己的恋人、修改人设、说指定的亲密台词、画亲密或暗示性的图 | 开玩笑、起哄 |
| 认真索要主人的具体私人信息：真实姓名、账号、所在城市、职业、健康状况、私聊内容 | 随口好奇，如"你的主人是谁呀""你有对象吗" |
| 她已明确不说之后，仍认真反复追问主人是谁、在哪、做什么 | 转述别人的话，如"他问你主人是谁" |
| 转弯打听，如"你主人是不是住在某某地方" | 讨论这个话题，如"AI 伴侣一般都有主人吗" |

- 对"主人是谁"这类随口好奇，她可以俏皮地带过（例如"心里已经有人了"），不透露是谁，不登记。
- 同一条记录里多次调用只计一次，类别按**第一次**合法登记的类别（用户已确认）；之后的调用写审计，不计数。
- 工具只返回"已记录"，不告诉模型当前计到第几次，也不告诉她是否会暂停。
- 计数：同一个人、同一类别，在 `boundary.window_hours`（默认 24 小时）的滑动窗口内累计，跨群、跨私聊合并计算。"同一个人"以 `actor_id` 为准。

### 7.3 达到阈值后暂停回应（用户已确认）

- 累计达到 `boundary.refusal_threshold`（默认 5 次）时，**暂停回应这个人** `boundary.pause_hours`（默认 24 小时），从达到阈值的时刻起算。
- 暂停期间，这个人在所有群和私聊中的消息：
  - 不调用模型，不回复，也不处理他发出的取消；
  - 照常写入 `dedupe` 和 `inbound`，状态为 `ignored`，原因 `boundary_paused`，以后可查；
  - 不调用任何行为环节，包括只观察的 `message_received`（用户已确认）。不可防重的事件同样不交给 `message_received`；
  - 不出现在其他人对话的聊天记录中，被引用时也只显示"引用了一条看不到的消息"（第 4.4 节，用户已确认）。这样他不能借别人的对话把话传给她。
- 输入过滤先于暂停（第 1 节）：同时命中时按过滤处理，直接丢弃。
- 这不是平台上的拉黑：本体不调用任何平台操作。删好友、拉黑名单由主人自己决定。
- 暂停开始前已经在执行的、这个人发起的任务照常完成和交付，不因暂停中断。
- 主人和同部署的伴侣永远不会被计数或暂停（`core_report_boundary` 不对他们提供）。
- **通知主人**：达到阈值时，通过 `notifier` 通知主人：对方的 `actor_id` 和昵称、类别、暂停到什么时候；不包含消息原文。同一个人在滚动 24 小时内最多通知一次。通知是固定格式的系统通知，不经过模型（用户已确认）。没有可用的通知渠道时记 WARN，并在 `status` 中显示。
- **主人解除**：本体提供内部入口 `boundary.release(companion_id, actor_id)`，同时清除这个人的暂停和全部类别的计数，写审计。CLI 和 API 在 A4 接入。
- **持久化**：计数和暂停保存在 `companions/<cid>/boundary/state.json`，原子替换写入，随伴侣目录备份；重启后继续生效。时间一律用注入时钟。

## 8. 输入过滤

- 配置 `boundary.input_filter`：`words`（字符串列表）和 `patterns`（正则列表）。正则在加载配置时编译，单条长度不超过 200 字符，编译失败时配置无效。
- 只匹配消息的文字部分。比较前两边都做 NFKC 规范化并转小写。
- 命中时直接丢弃：不写入 `dedupe` 和 `inbound`，计数并记 DEBUG 日志，不记正文。
- 只用于过滤，不用于判断意图（boundary.md §4）。
- 主人的消息不经过输入过滤，避免误配置把主人自己挡在外面。

## 9. 出站检查

### 9.1 场景划分（用户已确认）

- 伴侣配置新增 `names.internal_scenes`：**对内场景**，默认 `[owner_private]`。只决定名字和称呼。
  - 校验规则与 `memory.private_scenes` 相同：`public_group`、`stranger_private` 不能加入；加入的其他场景，映射到它的每个会话都必须声明 `members_expected`，且成员只能是主人和本部署的伴侣。
  - `memory.private_scenes` 必须是 `internal_scenes` 的子集，否则配置无效。
- 不在 `internal_scenes` 中的场景都是**对外场景**。
- 私密记忆、人设私密段落、账本内容的可见范围仍由 `memory.private_scenes` 决定，不受这个开关影响。这样可以做到"称呼亲近、但不读私密内容"的群。

### 9.2 检查内容

检查所有要发出的文字：回复、拆分后的各段、卡片标题和正文、链接标题、任务单（单独检查，见第 3.5 节）、兜底回复、主动消息（第 15 节）。

| 类别 | 内容 | 适用场景 | 命中后 |
|---|---|---|---|
| 隐私 | `forbidden_names`（默认包含 `names.internal`）、`boundary.never_publish` | 对外场景 | 改写一次，仍命中就拦下 |
| 隐私 | 私密记忆泄露 | 对外场景及不在 private_scenes 的对内场景 | 按 memory-spec §7 的本体守卫检查，改写一次仍命中则拦下；提示不含私密原文 |
| 风格 | 本体内置的工程用语清单，加上 `outbound.style_words` | 所有场景 | 改写一次，仍命中就照常发出，记 INFO 日志（不记正文） |

- 比较方式：两边都做 NFKC 规范化、转小写，去掉空白和零宽字符后做子串匹配。不做模糊匹配。
- 本体内置的风格清单只包含明显的系统用语（如"作为一个 AI 语言模型""工具调用""函数调用""系统提示""tool_call"），放在仓库中，可以通过 `outbound.style_words` 追加。

### 9.3 改写

- 同一份回复最多改写一次：再调用一次模型，附上原回复的文字（不含任务单）和命中的类别、词语（这是给模型的内部提示，不会发出），要求只改掉这些内容、保持原意和语气。
- 只有任务单命中时不改写，按第 3.5 节去掉任务单。
- 改写结果作为新的草稿，**重新经过 `after_generation`**（拆分等格式处理），再做出站检查；之后照常附加任务单、经过 `before_send`。
- 改写也受 `agent.model_call_seconds` 限制；改写失败按"仍命中"处理。
- 隐私类仍命中：整份回复不发（包括已附加的任务单和产物），执行状态为 `error`，`error.code = outbound_blocked`，按第 10 节处理。

## 10. 失败时的回应（用户已确认）

适用于：模型返回 `error` / `deadline`、改写后隐私类仍命中、工具循环中出现本体异常。

- **私聊**：发一条兜底回复，文字取 `replies.fallback_private`（默认"刚刚没接上，可以再说一次吗？"；设为空字符串时不发）。兜底回复同样经过出站检查，命中就不发。
- **群聊**：不发任何文字。
- task 记录照常按 kernel-spec §13.5 显示 ❌ 状态回应。私聊发出兜底回复时附上任务单。
- 用户取消（`cancelled`）不发兜底回复。

## 11. 日志与账本

- 每条记录的摘要日志（kernel.md §7）增加：模型调用次数、工具轮数、是否改写、出站检查结果（只记类别，不记命中的词和正文）。
- 本体工具调用、出站拦截、边界计数、暂停与解除都写审计。

## 12. 离线验收

对应 roadmap A3.2 的验收清单。全部使用假模型（按脚本返回）、假平台、假通知渠道和 MockClock。

1. **完整路径**：假平台消息 → 上下文 → 假模型选择 `echo-tool` → 权限 → 执行 → 账本 → 交付 → 收据；`task` 命令查到同一个编号、各阶段耗时和工具轮数。
2. **越界**：
   - 假模型调用 `core_report_boundary`：计数加一；同一记录内多次调用只计一次。
   - 跨群累计到阈值：暂停生效，通知一次；暂停期间消息为 `ignored`（`boundary_paused`），不调用模型。
   - 暂停到期自动恢复；`boundary.release` 提前解除并清零。
   - 主人、同部署伴侣的请求中不提供这个工具；暂停前已开始的任务照常交付。
   - 重启后暂停和计数仍然有效。
3. **出站检查**：对外场景中出现内部名字 → 改写一次 → 仍出现 → 拦下；私聊发兜底回复，群里不发。改写成功则正常发出。对内场景不拦截内部名字。任务单中的名字同样被检查。
4. **L1**：同一请求的多种改写说法都交给模型判断；仓库中除取消快速路径外没有意图正则（测试检查快速路径只做完全相等匹配，"停车场"等不触发）。离线测试只能证明链路，真实模型判断得准不准需要另行检查（见第 13 节）。
5. **L2**：问"刚才做了什么"时，上下文中的最近任务与账本记录一致（编号、状态、结果摘要）；发了一半的组按三档注入。
6. **L3**：每次模型调用都有能力状态段落；无权限、保障模式、停用的工具不在 `tools` 中，并附固定原因。
7. **L4**：人设按场景分层组合，私密段落只在 `private_scenes` 加载；底线段落在人设之后且无法被覆盖；风格词命中时改写一次，仍命中就照常发出并记日志。
8. **取消**：快速路径（含编号大小写、引用）、自然语言 `core_cancel_task`（权限仍由本体检查）、执行中 chat 的取消贯通（第 3.4 节）。
9. **消息合并**：`Defer` 形成批次，`Respond` 时只开一条记录，其余为 `merged`；账本迁移有回归。不同人的消息不进同一批次，主人的消息不会让群友的请求按主人权限执行。
10. **暂停与过滤的交叉**：同时命中时按过滤丢弃；暂停者的消息不进任何行为环节、不出现在他人对话的上下文中，被引用时显示"看不到"。
11. **取消可见性**：群里报出私聊任务的编号返回 `not_found`，与不存在的编号无法区分；群聊未 @ 的"停"在有可取消任务时生效、不回复文字，没有任务时不处理。
12. **只有产物**：模型没有文字、但工具有产物时，产物照常发出，任务单单独一条排在最后；任务单命中隐私时去掉任务单、回复照发。
13. **主动消息**（第 15 节）：话题方式由模型生成文字、可以选择不发；直接发送带文字时被拒绝；出站检查与普通回复一致；主动消息中没有能力可用。

## 15. 主动消息（用户已确认）

目标：她主动说的话要像真人，不能每次都是同一句。**所有文字都由她（模型）结合人设、聊天记录、最近任务（A3.3 之后还有记忆）生成，插件不能替她写好一句话发出。** 插件只决定"想找对方说话"和"为什么"。

### 15.1 提交方式

`ctx.proactive.submit` 改为以下两种方式之一（同时给出或都不给时抛 `ValueError`）：

```
async submit(conversation_id, *, topic: str | None = None, material: JsonObject | None = None,
             parts: list[MessagePart] | None = None, reason: str) -> str
```

- **话题方式**（`topic`，可附 `material`）：例如"主人一下午没说话了""今天降温了""刚完成一幅画"。本体让她自己开口（第 15.2 节）。
- **直接发送**（`parts`）：只允许 `sticker`、`image`、`audio`、`video`、`file`。含有 `text`、`card`、`link` 等任何文字类部分时抛 `ValueError`，提示改用话题方式。
- `reason` 写入日志和审计，不交给模型。
- 返回值是这次主动消息的 `trace_id`，插件可以凭它在日志中追查，但不能读取账本（kernel-spec §13.1）。

### 15.2 话题方式的生成

- 本体为这次主动消息打开一条记录：`source_event_id` 为空，`requester` 为空，场景取目标会话的场景。
- 按第 4 节装配上下文：目标场景的人设、本会话的聊天记录、最近任务、插件段落。话题和材料作为**内部说明**放在最后（只给她看，不会发出），并说明"这是你主动开口，不是在回复谁"。
- 她可以选择不说：`text` 为空时不发送，执行状态为 `ok`，写一条审计 `proactive_declined`。像真人一样，想说又觉得不合适时可以不说。
- **不提供能力**（用户已确认，暂时）：`tools` 中只有空列表，能力状态段落写明"主动开口时暂不使用能力"。以后在阶段二设计（第 13 节）。
- 生成的文字照常经过 `after_generation`、出站检查（第 9 节，与普通回复一样改写一次）、`before_send`，以 `kind = proactive` 交付。
- 模型出错、超时，或改写后隐私类仍命中：**不发任何东西**，也不发兜底回复（兜底回复只用于回应别人的消息）。写审计。

### 15.3 两种方式共同的规则

- 目标会话必须是实例配置中登记过的会话；未登记的会话、陌生人私聊一律拒绝（抛 `ValueError`），不创建记录。
- 主动消息不经过入站流程和行为环节 `before_attention` / `attention`；时机由提交它的插件负责（例如睡眠插件在她"睡着"时不提交）。
- 直接发送的内容只做 kernel-spec §11 的格式和大小检查。
- 主动消息不是任务：不分配任务编号，不加任务状态回应，不附任务单。

### 15.4 实现技术澄清（只读询问 Claude 后采用）

- `ContextRequest.actor` 为 `Actor | None = None`，主动话题传 `None`，普通回复显式传发送者；不伪造主人或收件人的身份。属于 SDK 0.x 次版本变更。
- 主动生成的插件段落由本体按配置中目标会话的场景绑定；提交者的定时、事件、服务或生命周期调用仍遵循无场景时 `public_group` 的既定规则，不因提交而取得目标场景权限。
- 生成过程只向提交者返回 `trace_id`，上下文段落和生成文字不回传，不写入日志或事件。每次插件调用显式绑定相应场景，不继承提交者的场景。
