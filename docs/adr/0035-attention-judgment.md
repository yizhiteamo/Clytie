# ADR 0035：行为插件的轻量判断与被叫到的标记

状态：草案，随 `chat-behavior-spec.md` 一起确认。

## 问题

B7 要让她在群里自然接话，并且效果要好（用户 2026-11-22）。只靠规则判断"要不要接"不够自然，需要让模型想一想。但行为插件不能调用模型：模型调用由本体统一管理额度、审计、取消和隐私投影。

另外，插件要知道一条消息是不是在叫她：有没有 @ 她、是不是回复她的消息、有没有叫她的名字。"回复的是不是她"只有账本知道；名字配置里有内部名字，不能交给插件。

## 决定

1. `EventEnvelope` 新增 `addressed`，由本体在身份映射后填写：`mention`、`reply_to_self`、`name`（`internal` / `external` / 空）。只给类别，不给名字本身。
2. `attention` 新增返回值 `Judge(facts)`。本体在后台用本伴侣的同一个模型做一次轻量判断，然后带着结果再调用一次 `attention`。
3. 判断请求由本体组装：截取的场景人设、最近的聊天记录（按正式回复的可见性规则投影）、插件给出的固定字段事实。不带工具、记忆和图片。插件不能附加任意文字。
4. 结果是固定的 JSON：`join`、`focus`、`new_topic`、`calling_me`。审计记为 `model.usage`，`purpose = attention`。
5. `Respond` 可以带 `focus` 和 `recheck_after`。回复生成后，如果别人已经又发了很多条，本体再问她一次"还要发吗"。
6. 群聊安全带放在本体，可以调，不能关。
7. 边等边写（真实补测后追加，用户 2026-11-22 确认）：`Defer` 和 `Judge` 可以带 `prepare`。等待或判断期间，本体先发出正式回复的第一次模型调用。工具、出站检查和交付等插件最后返回 `Respond` 之后才进行。同一个人又发消息时，丢掉重写；只在批次等待期间重写，每批最多预写 3 次，之后按原流程写。补测中被叫到后约 10 秒才回复（叫名字约 13 秒），其中 3 秒是干等，叫名字时还有约 3 秒在判断。

## 不选的方案

- **让插件直接调用模型**：插件会拿到原始上下文，能绕过可见性投影、额度和审计。
- **每条消息都用完整上下文判断**：一次约 1 万 token 以上，群消息多时费用不可控。
- **只用规则**：保留为 `judge: rules` 选项和失败时的退路，但默认效果不够自然。
- **把名字交给插件自己匹配**：内部名字会离开本体。
- **安全带放在插件里**：不装说话时机插件时，她仍会回应每一个 @，别的机器人一直 @ 她的死循环照样会发生；停用插件也不能让保护消失。
- **只缩短合并等待**（3 秒改 1.5 秒）：只省约 1.5 秒，还是在干等；连发两条时更容易被分成两次回，反而更像机器。
- **预写期间就执行工具**：画图、记东西有副作用和费用，而预写可能被丢掉。
- **别人的消息也触发重写**：热闹的群里几乎每次都要重写，又慢又浪费。

## 影响

- SDK 0.16：只新增字段和返回值，已有插件不用修改。
- 新的审计用途 `attention` 和审计事件 `reply_withdrawn`、`safety_belt.tripped`；新的入站忽略原因 `safety_paused`。
- 判断会让自然接话晚 1–3 秒出现，被叫到和私聊不受影响。
- 每次判断约 1000–2000 token，用量在状态和审计中可查。
- SDK 0.17（补测后追加）：`Defer` 和 `Judge` 的 `prepare`，`TokenUsage.cached_input_tokens`。新的审计事件 `prepare_discarded`；`model.usage` 增加 `duration_ms`、`cached_input_tokens` 和 `prepared`。
- 被叫到和私聊的回复预计缩短到约 7 秒。同一个人连发、叫名字但不是在叫她时，会多花正式模型调用。
