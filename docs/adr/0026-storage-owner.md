# ADR 0026：伴侣存储所有者与固定快照线程

状态：依据用户批准的 storage-spec.md，待原型、实施及验收。不以本文宣称性能问题已解决。

## 原因与范围

Issue #72 的重复诊断在事件循环上的 file_lock/fsync 和 MemoryStore.transaction/commit 采到长停顿。有界故障注入证明两个同步入口会阻塞循环；没有据此推断 CI 底层设备的所有原因。选择每伴侣专用存储线程，避免公共线程池转交连接与关闭 SQLite 线程检查；不合并数据库或削弱持久性。

## 执行单元

StorageOwner 的启动工厂在线程内构造记忆/账本资源，关闭也在线程内完成；原生命周期与迁移核验仍先于 ready。异步端只保存命令入口、控制状态和独立结果。同步本体实现可保留在所有者内部，但外层不得拿到 store/db/cursor 后自行读写。读改写合成一条受控命令，不能逐条 SQL 跨 await。

命令持有稳定的本次请求标识、可信上下文、取消标记及结果跟踪；事务与文件阶段仍用原业务/管理编号和持久证据。结果交回事件循环通过线程安全通知，等待者取消不取消底层执行状态。业务代码不能通过传入任意插件回调绕过边界；外部模型及平台调用从快照取得参数，在所有者之外运行。

普通容量与收尾凭证分开计数，执行使用同一就绪 FIFO。16 个收尾凭证保留的是完整责任，不是预先入队的空命令；一个凭证任意时刻最多一个就绪/执行命令，允许依次记录发送前状态、收据、重试决定、最终/迟到结果及审计。未结束的外部执行者不能归还凭证，重复归还幂等。普通请求最多 64 个未完成项；不使用隐藏的无限等候列表。

状态转换与容量计数使用进程内同步保护，不能在锁内做文件 I/O 或等待事件循环。cancel/stop/status 为控制状态通知，不依赖普通槽位；命令从 queued 到 running、提交开始与取消的先后须可确定性注入测试。所有者等待不是业务超时来源，期限由注入 Clock 驱动。

## 捕获线程和锁顺序

业务线程持有运行库，快照线程拥有独立只读库；每个连接保持创建线程检查。捕获屏障在上一逻辑操作结束后建立，在现有跨进程门闩内协同固定只读视图及关联状态。异步 provider.capture 仍由宿主执行，捕获身份沿异步调用链传播，SDK 本体存储入口据此拒绝重入；不能只检查当前线程，也不能错误拒绝其他等待中的正常业务。

只读线程从打开、固定读事务、物化到关闭始终拥有连接，返回不透明内部句柄而非连接本身。屏障释放后复制不占业务队列；取消后等待实际线程和视图释放，不能以 async task 已取消代替。具体 sqlite backup 逐批回调和稳定视图行为先经 storage-spec §6 原型验证。

锁顺序沿用生命周期/迁移保护 → 固定排序的捕获门闩 → 数据库事务。plugin-versions.metadata 的实现与规则不变。任何文件或数据库不可抢占调用跨过工程期限，记录超限、禁止发布迟到成功并继续跟踪真实释放；不声称已抢占。

## 跨库及关联持久链路清单

以下是源码核对的起始清单，实施时须补齐实际入口、故障注入和证据；本表不声明跨库整体原子性。

| 链路 | 当前持久边界及实施核对 |
|---|---|
| core_remember/core_forget | memory/context.py 调用记忆修订/写入，随后在账本追加 core.tool 审计；记忆自身修订与审计为本库事务，核对 trace/调用结果在中间崩溃时的既有证据，不自动重复记忆操作 |
| 回想窗口及提交 | memory/scheduler.py 从账本取窗口/高水位，再在记忆库提交记录及进度；把关联读取固定为快照，外部计算后校验，记录与进度同事务不拆开；账本通知审计不是第二个记忆提交 |
| 工具及发送 | kernel/service.py、delivery.py 在账本登记执行/发送，然后外部调用，再持久记录结果；凭证覆盖完整责任及多次写入；强杀后按原 interrupted/unknown 规则，不重放 |
| 边界暂停 | agent/policy.py 的账本审计、内存计数和 boundary/state.json 在共同捕获协调内；原文件与数据库并非一个 SQLite 事务，需核对失败/恢复证据，不把持锁描述成跨文件原子提交；通知在所有者之外 |
| 管理导入/恢复/公钥 | api/management_journal.py、memory/transfer.py、package.py 的事务标记、关联快照及文件发布/审计核验继续使用；线程改变不跳过日志和恢复阻止状态 |
| 资产与账本引用 | 先校验发布内容、持久登记归属，再返回 AssetRef，后续写入账本；原资产协调与捕获关联证明保留，不能因 owner 只管两库而漏掉登记/引用边界 |
| 完整实例捕获与恢复 | backup/runtime_capture.py 固定库/进度/边界与资产关联，restore.py 核验包及管理证据；所有者不替代来源保护、恢复受阻和第二写入者排除 |

所有外层 .db 访问、同步查询及 changed/通知回调需逐项分类：移入完整同步命令、改为异步取快照，或保留在线程外的外部副作用。不能将会安排 asyncio 任务的原业务方法原封不动放进线程。发现既有批准保证缺少恢复协议时报告用户，不补造新协议。

## 停止、恢复和验证顺序

停止先关新业务入口，继续受保护收尾与插件停止回调，最后由所有者关闭。普通伴侣超时强杀与管理/迁移例外保持；线程崩溃或未知状态不创建第二个所有者。恢复读取原日志和提交事实，不持久化/重放通用命令队列，也不在无证据时重新执行原操作。

先完成真实 SQLite 原型，再测容量/FIFO/取消，再转换生产连接和领域命令、外部调用收尾、备份屏障及停止链路，最后做完整组合和性能。四规模每种至少三组交替，双平台固定方法；不能用旧异常基线放宽门槛。新增节流策略或放宽目标需要用户确认。完整流程及验收数字以 storage-spec §9–§11 为准。
