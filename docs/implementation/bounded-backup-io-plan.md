### 备份源导入恢复的槽位交接待确认

静态调用链核对发现，Transfers.apply 的 _prepare_live 已登记 materializing 并可能物化/迁移库，随后 owned_snapshot 在另一线程捕获/复制，最后才进入 _apply_loaded 事务。只在最后事务前取得恢复槽位会遗漏前段失败；只在异常恢复时申请，控制 EOF 后通道可能已经断开；提前持槽又让现有捕获线程独立申请，会等待自身。不能把这些情形擅自改成不恢复或已取消。

建议由设计审查会话明确同一已接受管理操作的独占槽位凭证与串行借用：准备前取得，捕获、文件线程和 Owner 按明确执行边界交接，事务及必要恢复实际结束后释放；连接始终归各自原执行者，不传递连接或任意上下文、不允许并行借用。另一方向是重分准备与快照的持久阶段及恢复协议，影响更大。这里仅记录待确认方案，不修改现行产品规则或宣称已实现。
