# Issue #72 实施清单

依据：用户批准的 storage-spec.md 和 ADR 0026。沿用 m4-3，不切换审查流程；正式预算已用 1/3。本文是开发检查点，不是验收结论。

目标：让运行记忆/账本有唯一线程所有者，保留事务、权限、恢复和持久性，同时满足批准的双轴性能目标。

技术：Python 专用线程、线程安全控制通知、SQLite WAL、现有跨进程锁、MockClock。初始实现不引入公共线程池连接共享、数据库合并、通用跨库日志或新节流策略。

## 6. 生产接线与待完成验证

- 运行连接由 storage/runtime.py 工厂在所有者线程创建，StoreHandle 只作为事件循环内的受控命令入口；默认线程检查保留。场景和在场租约仍使用原有效期，排队不能延长私密可见性。FrozenDict 保持映射含义，不转成键元组。
- 工具、模型、发送、状态回应及 record 根责任复用收尾凭证；迟到执行者、持久结果及审计结束才释放。入站接受仍需普通容量；满时明确 storage_busy，不先 claim 后假成功。取消 receive 等待者不遗弃真实接受任务。
- 现有十六个收尾名额中，伴侣启动时固定保留一个用于停止；不是第十七个槽位。停止回调共享这一责任，命令就绪后才排入 FIFO；额外并发停止写入明确忙碌，不在另一个无界队列等待。真实回调及入队命令结束前不关库。
- 静默应用与 IPC 读取分离：一个有界、顺序的应用执行者，控制元数据最多六十四条（含在途），真正应用后才确认；后续 stop、escalate 和管理取消仍可受理。停止时未开始项不延长关闭，在途工作继续跟踪。原静默五秒未确认重启规则不变。
- 在线管理保留原 MemoryAPI、Journal、快照关联和恢复规则；完整存储命令进所有者，导入器留在外部异步边界，解密、加密和临时库在专用文件执行者。HTTP 断线不会变成执行者退出。停止后管理进程路径不变。
- 备份生命周期文件锁、配置检查和关联状态读取移出事件循环；只读快照线程保持固定视图直到复制真正完成。Operations.metadata 不变。
